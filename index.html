Платформа .NET и CLR

0/5

Что такое .NET, CLR и IL?

Коротко: .NET — платформа и экосистема для разработки: runtime, библиотеки, инструменты. CLR (Common Language Runtime) — виртуальная машина .NET: управляет выполнением кода, памятью (GC), безопасностью типов. IL (Intermediate Language / MSIL / CIL) — промежуточный байткод, в который компилируется C# (и F#, VB), до запуска JIT-компилятором превращается в машинный код.

Подробнее:

C#-код → [компилятор] → IL (в DLL/EXE) → [JIT при запуске] → машинный код CPU

Благодаря IL один и тот же .NET-код работает на разных ОС/архитектурах (cross-platform). Плюс: JIT знает конкретный CPU и может оптимизировать под него. AOT (Ahead-of-Time) — альтернатива JIT: компилирует сразу в машинный код (быстрый старт, но без runtime-оптимизаций).

Подводные камни: CLR + JIT дают холодный старт: первый вызов метода компилируется. В длинноживущих сервисах это не проблема, для серверлес (cold start) — критично; там используют AOT или предварительный прогрев.

Какие версии .NET сейчас актуальны и что нового? (состояние на 2026)★

Коротко: В продакшне сейчас .NET 10 — LTS-релиз, вышел в ноябре 2025, поддержка до ноября 2028. Параллельно идут превью .NET 11 (STS): релиз намечен на 10 ноября 2026, поддержка до ноября 2028, вместе с ним выходит C# 15. Главное практическое: .NET 8 и .NET 9 оба снимаются с поддержки 10 ноября 2026 — если проект на них, апгрейд нужно планировать сейчас.

Подробнее — релизный цикл: новая мажорная версия каждый ноябрь; чётные — LTS (3 года), нечётные — STS. Раньше STS жил 18 месяцев, теперь сроки выровняли так, что соседние LTS и STS заканчиваются одновременно — отсюда общая дата для .NET 8 и 9.

Что назвать из нового по версиям: - C# 12 (.NET 8): primary constructors, collection expressions [1, 2, 3]. - C# 13 (.NET 9): params для любых коллекций, System.Threading.Lock, HybridCache. - C# 14 (.NET 10): extension members (расширяющие свойства и static-члены, не только методы), ключевое слово field в свойствах, null-conditional assignment (obj?.Prop = value), file-based apps (dotnet run app.cs без csproj). - .NET 11 / C# 15 (превью, релиз в ноябре 2026): заголовочная фича — Runtime Async: асинхронность переезжает на уровень рантайма, что даёт чистые стек-трейсы и меньше накладных расходов вместо генерации state machine компилятором. Ещё: сжатие Zstandard, CoreCLR для WebAssembly, в C# 15 — аргументы в collection expressions ([with(capacity: n), .. items]).

Подводные камни: вопросом «на какой версии ваш проект и почему» проверяют понимание LTS vs STS и цены апгрейда, а не знание changelog наизусть. Сильный ответ: «в продакшне держим LTS — сейчас это .NET 10; апгрейд между соседними версиями обычно дешёвый: поднять TargetFramework и пакеты, прогнать тесты. За .NET 11 слежу из-за Runtime Async, но в прод возьму после GA». Не выдавай превью-фичи за то, что уже работает в проде — это ловит любой сильный интервьюер.

Статическая vs динамическая типизация

Коротко: Статическая — типы проверяются компилятором, ошибки до запуска (C#, Java, Go). Динамическая — типы проверяются в рантайме, переменная может менять тип (Python, JavaScript).

Подробнее: C# — строго статически типизированный, но имеет dynamic (проверки откладываются в рантайм), var (вывод типа компилятором, тип всё равно статичен), object (любой тип, но boxing). Строгая/нестрогая типизация — отдельная ось: допускаются ли неявные преобразования типов.

Подводные камни: dynamic обходит проверки компилятора — ошибки обнаружатся только в проде. Используется для COM-взаимодействия, работы с DLR (IronPython) и редких задач рефлексии. В обычном коде — избегай.

Как устроен GC в .NET (кратко)?

Коротко: сборщик мусора автоматически освобождает память объектов, на которые больше нет ссылок. Работает по поколениям: Gen 0 (новые объекты, собирается часто и быстро), Gen 1 (буфер), Gen 2 (долгожители, собирается редко и дорого).

Подробнее: идея поколений — «большинство объектов умирают молодыми». Объекты > 85 КБ попадают в Large Object Heap (LOH), который собирается вместе с Gen 2. Во время сборки GC строит граф достижимости от корней (стек, статические поля) — всё недостижимое освобождается.

Подводные камни: GC.Collect() вручную — почти всегда антипаттерн. Финализаторы (~Class()) задерживают освобождение объекта минимум на одну сборку — для освобождения ресурсов используй IDisposable, а не финализатор. Утечки в .NET реальны: подписка на событие долгоживущего объекта держит подписчика в памяти.

Как GC обрабатывает циклические зависимости?

Коротко: .NET GC использует трассировку достижимости (не подсчёт ссылок), поэтому циклические ссылки не вызывают утечек: если на цикл A→B→A нет «корней» (стека, статики), оба объекта собираются.

Подробнее: Корни GC: локальные переменные на стеке, статические поля, регистры CPU, GC handles. GC строит граф достижимости от корней — всё, до чего нельзя дотянуться, удаляется. Именно поэтому COM-подсчёт ссылок страдал от циклов, а .NET — нет.

Подводные камни: Утечки в .NET всё равно возможны — через «живые» корни: статическое поле хранит список → список держит объекты → объекты никогда не соберутся. Типичные причины: подписка на событие долгоживущего объекта (static event + лямбда с захватом this), кэши без вытеснения (Dictionary, который только растёт), таймеры и фоновые задачи, держащие ссылки на объекты. Профилировать: dotnet-counters, dotMemory, PerfView.

C# — типы и память

Value types vs reference types. Что где хранится (stack/heap)?★

Коротко: value types (int, bool, struct, enum) хранят данные напрямую и копируются при присваивании; reference types (class, string, массивы, делегаты) хранят ссылку на объект в куче — при присваивании копируется только ссылка.

Подробнее: локальная переменная value type обычно живёт на стеке, объект класса — в куче, а переменная хранит адрес. Следствие: изменение копии struct не влияет на оригинал, изменение объекта по второй ссылке — влияет.

Подводные камни: «value types всегда на стеке» — упрощение, за которое цепляются интервьюеры. Value type, являющийся полем класса, лежит в куче внутри объекта. Элементы int[] — тоже в куче. Правильная формулировка: value type хранится там, где живёт его контейнер.

var p1 = new PointStruct { X = 1 };
var p2 = p1;            // копия
p2.X = 99;              // p1.X всё ещё 1

var c1 = new PointClass { X = 1 };
var c2 = c1;            // копия ссылки
c2.X = 99;              // p1.X теперь 99 — объект один

Может ли value type оказаться в куче?new

Коротко: Да, и довольно часто. Правило «value type всегда в стеке» — миф. Куда попадёт значение, определяет не тип, а место хранения: локальная переменная живёт в стеке, а поле объекта живёт там же, где сам объект — в куче.

Подробнее: пять случаев, когда значимый тип оказывается в куче: 1. Поле класса. class Order { public int Id; } — Id лежит внутри объекта Order, то есть в куче. 2. Боксинг. object o = 42 — значение копируется в объект-обёртку в куче. 3. Элемент массива. int[] arr — сам массив всегда объект в куче, значения лежат внутри него. 4. Захват замыканием. Локальная переменная, попавшая в лямбду, переносится в скрытый класс-контейнер в куче. 5. Локальные переменные async-метода, переживающие await, — они переезжают в объект state machine.

Подводные камни: это классический вопрос-ловушка, который проверяет, не заучил ли ты фразу из учебника. Правильная формулировка: «значимый тип хранится по значению (переменная содержит сами данные), ссылочный — по ссылке; а стек или куча — следствие того, где объявлено хранилище». Именно эта формулировка снимает все follow-up-вопросы.

struct Point { public int X, Y; }

class Shape
{
    Point _origin;         // в куче — внутри объекта Shape
}

void Method()
{
    Point p;               // в стеке — локальная переменная
    Point[] points = new Point[10];   // в куче — массив всегда объект
    object boxed = p;      // в куче — боксинг, создана копия
}

Что такое boxing и unboxing? Почему это плохо?★

Коротко: boxing — упаковка value type в object: в куче создаётся объект-обёртка, и значение копируется туда. Unboxing — явное извлечение обратно через приведение типа.

Подробнее: boxing вызывает аллокацию в куче → нагрузка на GC. В горячем цикле тысячи boxing-операций заметно бьют по производительности. Где случается неявно: не-generic коллекции (ArrayList), передача struct в параметр типа object, вызов ToString()/GetHashCode() у struct без их переопределения, конкатенация "x = " + 5 (в старых паттернах).

Подводные камни: unboxing требует точного типа: если в object лежит int, то (long)o бросит InvalidCastException — сначала (int)o, потом расширение. Как избежать boxing: generics (List<int> вместо ArrayList), переопределение ToString() у struct, интерфейсы через generic-constraint, а не через object.

object o = 42;          // boxing: аллокация в куче
int i = (int)o;         // unboxing: ок
long l = (long)o;       // InvalidCastException!
long l2 = (int)o;       // правильно: сначала unbox в int

struct vs class — когда что выбирать?

Коротко: class — reference type, поддерживает наследование, живёт в куче. struct — value type, копируется целиком, наследование запрещено (только интерфейсы). Struct — для маленьких неизменяемых данных-значений.

Подробнее: ориентир из гайдлайнов Microsoft: struct уместен, если тип маленький (условно до ~16 байт), логически представляет единое значение (координата, деньги, диапазон дат), неизменяемый и не будет боксироваться массово. Всё остальное — class.

Подводные камни: изменяемые (mutable) struct — источник трудноуловимых багов: методы меняют копию, а не оригинал. Хорошая практика — readonly struct. Для DTO с value-семантикой в современном C# часто удобнее record / record struct.

public readonly struct Money
{
    public decimal Amount { get; }
    public string Currency { get; }
    public Money(decimal amount, string currency) => (Amount, Currency) = (amount, currency);
}

Какие ограничения у конструкторов и финализаторов в структурах?new

Коротко: У структуры не может быть финализатора (деструктора ~Foo()) — финализация работает только для объектов в куче, которыми управляет GC. Конструкторы разрешены, но с ограничениями: до C# 10 нельзя было объявить конструктор без параметров, и любой конструктор обязан присвоить все поля.

Подробнее: ключевые правила: - Безпараметрический конструктор у структуры существует всегда и обнуляет все поля (default). С C# 10 его можно объявить явно, но он не вызывается при new T[10] или default(T) — массив всё равно заполнится нулями. - Конструктор структуры обязан инициализировать каждое поле, иначе ошибка компиляции (у класса поля молча получают значения по умолчанию). - Наследоваться структура не может, поэтому base()-вызова у неё нет, а this() — есть. - Освобождение ресурсов у структуры делают через IDisposable + using, не через финализатор.

Подводные камни: классический follow-up — «почему у структуры не может быть деструктора?». Ответ: финализатор — это механизм GC для управляемой кучи, а значимый тип может лежать в стеке и уничтожается детерминированно вместе с областью видимости, так что финализировать там нечего.

struct Money
{
    public decimal Amount;
    public string Currency;

    public Money(decimal amount, string currency)
    {
        Amount = amount;         // обязаны присвоить ОБА поля
        Currency = currency;
    }

    // ~Money() { }   // ❌ CS0575: структура не может иметь финализатор
}

var arr = new Money[3];   // конструктор не вызывался — все поля default

Может ли структура реализовывать интерфейс?new

Коротко: Да, может — но не может наследоваться от класса или другой структуры (все структуры неявно наследуются от System.ValueType). Ловушка вопроса в другом: приведение структуры к интерфейсу вызывает боксинг, и все преимущества значимого типа теряются.

Подробнее: при IShape s = myStruct значение копируется в объект в куче. Дальше два неприятных следствия: (1) появляется аллокация там, где её не ждали; (2) если у структуры есть изменяющие методы, они меняют копию в боксе, а не исходную переменную. Обойти боксинг можно generic-ограничением where T : IShape — тогда JIT генерирует специализированный код для конкретной структуры, и упаковки не происходит.

Подводные камни: практический вывод — структуры делай неизменяемыми (readonly struct), это убирает целый класс багов с «поменял, а не изменилось». Ещё частый follow-up: при реализации интерфейса структурой методы Equals/GetHashCode из ValueType работают через рефлексию и медленны — для структур, попадающих в словарь, переопределяй их вручную или используй record struct.

interface IArea { double Area(); }

readonly struct Circle(double r) : IArea       // структура реализует интерфейс
{
    public double Area() => Math.PI * r * r;
}

var c = new Circle(2);
IArea boxed = c;                    // ❌ боксинг: копия уехала в кучу

static double Sum<T>(T shape) where T : IArea  // ✅ без боксинга
    => shape.Area();

ref, out и in — в чём разница?

Коротко: все три передают параметр по ссылке. ref — переменная должна быть инициализирована до вызова, метод может читать и писать. out — метод обязан присвоить значение до выхода. in — только чтение, метод менять не может.

Подробнее: out — идиома «вернуть несколько значений» и паттерн TryParse. in придуман для передачи больших struct без копирования, сохраняя гарантию неизменности.

Подводные камни: сегодня вместо out-параметров для нескольких результатов часто чище вернуть кортеж (bool ok, int value) или record. Упомянуть это — плюс в карму.

if (int.TryParse(input, out var number))   // out: TryParse обязан присвоить
    Console.WriteLine(number);

void AddDays(ref DateTime date) => date = date.AddDays(1);  // ref: читаем и пишем

Nullable типы: `int?` и nullable reference types (NRT)

Коротко: int? — это Nullable<int>, обёртка, позволяющая value type принимать null (HasValue / Value). Nullable reference types (C# 8+) — статический анализ компилятора: string считается «не null», string? — «может быть null», нарушения дают предупреждения.

Подробнее: в шаблонах проектов начиная с .NET 6 NRT включены по умолчанию (<Nullable>enable</Nullable>). Операторы для работы с null: ?? (значение по умолчанию), ?. (безопасный вызов), ??= (присвоить, если null), ! (null-forgiving — «я знаю, что тут не null»).

Подводные камни: NRT — не рантайм-гарантия. Это только предупреждения компилятора: null всё равно может прилететь из рефлексии, десериализации JSON или библиотеки без аннотаций. Поэтому на границах системы (входящие DTO) валидация всё равно нужна.

int? age = null;
int result = age ?? 0;              // 0, если null

string? name = FindName(id);        // может вернуть null
Console.WriteLine(name?.Length);    // безопасно: null, если name == null

Почему string неизменяемый и когда нужен StringBuilder?

Коротко: string в .NET immutable — любая «модификация» (+, Replace, ToUpper) создаёт новый объект. В циклах с множеством конкатенаций это лавина аллокаций — там нужен StringBuilder.

Подробнее: неизменяемость даёт потокобезопасность, возможность кэшировать hash code (строки — частые ключи словарей) и безопасное разделение одной строки между кусками кода. StringBuilder держит внутренний буфер и дописывает в него без создания промежуточных строк.

Подводные камни: для 2–5 конкатенаций или интерполяции $"..." StringBuilder не нужен — компилятор и так справится эффективно (string.Concat). Правило: цикл + конкатенация = StringBuilder, разовая сборка строки — интерполяция.

var sb = new StringBuilder();
foreach (var line in lines)
    sb.AppendLine(line.Trim());
var result = sb.ToString();

Строки: интернирование, сравнение и работа без лишних аллокацийnew

Коротко: Строки в .NET неизменяемы, поэтому любая «модификация» создаёт новую строку. Одинаковые строковые литералы автоматически интернируются — хранятся в общем пуле в одном экземпляре. Сравнивать строки нужно явно указывая правила: == сравнивает содержимое посимвольно (ordinal), а вот ToLower() == ToLower() — это две лишние аллокации и потенциальный баг с культурой.

Подробнее: что важно назвать: - Интернирование работает для литералов на этапе компиляции; строки, собранные в рантайме, в пул не попадают (можно вручную через string.Intern, но это редко нужно). - StringComparison: Ordinal — быстрое побайтовое сравнение (для ключей, идентификаторов, путей); OrdinalIgnoreCase — регистронезависимое без учёта культуры; CurrentCulture — для текста, который видит пользователь (сортировка имён). - Классический пример культурной ловушки: в турецкой локали "I".ToLower() даёт "ı", и сравнение логинов ломается. Отсюда правило: для служебных строк всегда Ordinal. - StringBuilder — для конкатенации в цикле; для 2–3 строк подряд обычная интерполяция быстрее. - Span<char> / ReadOnlySpan<char> — срез строки без аллокации: text.AsSpan(0, 10) вместо Substring(0, 10). Хороший бонусный ответ на вопрос про оптимизацию.

Подводные камни: (1) string.Empty vs "" — эквивалентны, но string.IsNullOrEmpty / IsNullOrWhiteSpace читаются лучше, чем ручные проверки. (2) Конкатенация в цикле — самая частая ошибка производительности на собеседовании: 10 000 итераций создадут 10 000 промежуточных строк. (3) == для строк — это перегруженный оператор, сравнивающий значения, а не ссылки; но object.ReferenceEquals покажет разницу, и на этом строят каверзные вопросы про интернирование.

string a = "hello";
string b = "hello";
Console.WriteLine(ReferenceEquals(a, b));   // True — литералы интернированы

string c = new string("hello".ToCharArray());
Console.WriteLine(ReferenceEquals(a, c));   // False — создана в рантайме
Console.WriteLine(a == c);                  // True — сравнение по значению

// служебные строки — только Ordinal
if (role.Equals("admin", StringComparison.OrdinalIgnoreCase)) { }

// цикл — только StringBuilder
var sb = new StringBuilder();
foreach (var item in items) sb.Append(item).Append(", ");

// срез без аллокации
ReadOnlySpan<char> prefix = fileName.AsSpan(0, 3);

IDisposable и using — зачем нужны, если есть GC?★

Коротко: GC освобождает управляемую память, но ничего не знает о внешних ресурсах: файловых дескрипторах, сетевых соединениях, подключениях к БД. IDisposable.Dispose() — контракт детерминированного освобождения таких ресурсов, а using гарантирует его вызов даже при исключении.

Подробнее: using разворачивается компилятором в try/finally { Dispose(); }. С C# 8 есть using-declaration без скобок — ресурс освобождается в конце области видимости. Если твой класс владеет полем IDisposable (например, хранит FileStream) — реализуй IDisposable сам и прокинь Dispose внутрь. Для асинхронного освобождения есть IAsyncDisposable + await using.

Подводные камни: (1) Dispose должен быть идемпотентным — повторный вызов не должен ломать объект. (2) Классическая ловушка: HttpClient не оборачивают в using на каждый запрос — это ведёт к socket exhaustion (исчерпанию сокетов в TIME_WAIT). Правильно: один долгоживущий экземпляр или IHttpClientFactory. Этот follow-up обожают спрашивать.

// using-declaration (C# 8+)
using var stream = new FileStream(path, FileMode.Open);
// ... работа с файлом
// Dispose() вызовется автоматически в конце области видимости

public sealed class ReportWriter : IDisposable
{
    private readonly StreamWriter _writer = new("report.txt");
    public void Dispose() => _writer.Dispose();   // владеем — освобождаем
}

Как выглядит стандартная реализация Dispose-паттерна?new

Коротко: Полный паттерн нужен, только если класс владеет неуправляемым ресурсом (хендл, указатель). Он состоит из публичного Dispose(), защищённого Dispose(bool disposing), вызова GC.SuppressFinalize(this) и финализатора как страховки. Если класс владеет лишь managed-полями (FileStream, HttpClient) — достаточно простого Dispose() без финализатора, а класс лучше сделать sealed.

Подробнее: зачем параметр disposing. При явном вызове (disposing: true) можно освобождать и управляемые, и неуправляемые ресурсы. При вызове из финализатора (disposing: false) трогать managed-поля нельзя — GC мог уже собрать их в произвольном порядке. GC.SuppressFinalize(this) снимает объект с очереди финализации: без него объект переживёт лишнюю сборку мусора и попадёт в старшее поколение. Асинхронный аналог — IAsyncDisposable + DisposeAsync() + await using, он нужен, когда освобождение делает I/O (сброс буфера, закрытие соединения).

Подводные камни: (1) Финализатор ради managed-полей — вред, а не польза: он замедляет сборку мусора и ничего не даёт. В современном коде неуправляемые ресурсы почти всегда прячут в SafeHandle, который уже реализует финализацию правильно. (2) Dispose() должен быть идемпотентным — флаг _disposed обязателен. (3) Из Dispose() не бросают исключения.

public class ResourceHolder : IDisposable
{
    private IntPtr _handle;              // неуправляемый ресурс
    private FileStream? _stream;         // управляемый ресурс
    private bool _disposed;

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);       // финализатор больше не нужен
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;           // идемпотентность
        if (disposing)
            _stream?.Dispose();          // managed — только при явном вызове
        if (_handle != IntPtr.Zero)      // unmanaged — освобождаем всегда
        {
            NativeMethods.CloseHandle(_handle);
            _handle = IntPtr.Zero;
        }
        _disposed = true;
    }

    ~ResourceHolder() => Dispose(disposing: false);   // страховка
}

Объект, класс, метод — базовые определения

Коротко: Класс — шаблон (тип), описывающий структуру и поведение. Объект — конкретный экземпляр класса в памяти. Метод — функция внутри класса, реализующая поведение.

Подробнее: Аналогия: класс — чертёж дома, объект — конкретный дом по этому чертежу. Несколько объектов одного класса независимы: new Order(1) и new Order(2) — разные объекты в куче, с разными Id, но одним и тем же поведением. Метод — именованный блок кода с сигнатурой (имя + параметры + возвращаемый тип).

Модификаторы доступа в C#★

Коротко: Определяют, кто может обращаться к члену или типу.

Модификатор Доступен из
public Везде
private Только внутри класса/структуры
protected Класс и его наследники

Подводные камни: internal — мощный инструмент: по умолчанию классы между проектами закрыты, не надо объявлять всё public. InternalsVisibleTo открывает internal для тестового проекта. Default-доступность: поля/методы класса — private, классы на уровне namespace — internal.

Виды классов в C#: static, abstract, sealed, partial, record

Коротко: Каждый модификатор добавляет ограничения или возможности к обычному классу.

Подробнее: - static class — нельзя создать экземпляр, нет конструктора, только статические члены. Используется для extension methods, утилит. - abstract class — нельзя инстанциировать напрямую; может иметь абстрактные методы (без реализации), которые обязаны переопределить наследники. - sealed class — запрещает наследование. String — sealed для безопасности и производительности. - partial class — класс разбит по нескольким файлам (компилятор склеивает); активно использует code generation (EF, WinForms, source generators). - record — value-семантика: равенство по полям, with, деконструкция (разобрано в разделе 1).

Подводные камни: В static class нельзя иметь instance-члены и нельзя реализовывать интерфейсы. sealed на override-методе (не на классе) запрещает дальнейшее переопределение ниже по иерархии.

public static class StringExtensions
{
    public static bool IsNullOrEmpty(this string? s) => string.IsNullOrEmpty(s);
}

Какие бывают свойства в C# и чем они отличаются от полей?new

Коротко: Свойство — это пара методов get/set, которая внешне выглядит как поле. Оно даёт инкапсуляцию: можно добавить валидацию, логирование или вычисление, не меняя код вызывающих. Поле — это просто ячейка памяти; в публичном API полей не держат.

Подробнее: виды свойств, которые стоит назвать: - Автосвойство: public string Name { get; set; } — компилятор сам создаёт скрытое backing-поле. - Только для чтения: { get; } — присвоить можно лишь в конструкторе или инициализаторе. - init (C# 9): присвоить можно только при создании объекта — основа неизменяемых DTO и record. - required (C# 11): компилятор обязывает задать свойство в инициализаторе объекта. - Вычисляемое: public bool IsExpired => DateTime.UtcNow > ExpiresAt; — без хранения, считается при каждом обращении. - С разными модификаторами: public int Id { get; private set; }. - Индексатор: public T this[int index] { get; set; } — обращение по obj[i]. - field (C# 14): даёт доступ к backing-полю прямо в аксессоре, без объявления поля вручную.

Подводные камни: (1) Свойство — это вызов метода, поэтому в свойстве не должно быть тяжёлой логики и побочных эффектов: order.Total не должно ходить в базу. (2) Автосвойства нельзя использовать в ref/out (это не переменная). (3) Замена публичного поля на свойство — ломающее изменение на уровне бинарной совместимости, поэтому публичные поля не заводят с самого начала.

public class Order
{
    public required string Number { get; init; }      // обязательное, неизменяемое
    public decimal Total { get; private set; }        // менять может только сам класс
    public bool IsPaid => PaidAt is not null;         // вычисляемое

    private DateTime? PaidAt { get; set; }

    // C# 14: field — доступ к backing-полю без ручного объявления
    public int Quantity
    {
        get => field;
        set => field = value > 0 ? value : throw new ArgumentOutOfRangeException(nameof(value));
    }
}

const vs readonly vs static readonly

Коротко: const — константа времени компиляции, значение «вшивается» в вызывающий код. readonly — присваивается при объявлении или в конструкторе, значение определяется в рантайме. static readonly — одно значение на тип, вычисляемое в рантайме.

Подробнее: const работает только с примитивами и строками. readonly подходит для любых типов, включая ссылочные.

Подводные камни: классический вопрос — versioning problem. Если библиотека A объявила public const int MaxSize = 10, а проект B её использует, то значение 10 скопировано в бинарник B. Обновили библиотеку до 20 — B продолжит видеть 10, пока его не перекомпилируют. static readonly читается в рантайме и такой проблемы не имеет. Поэтому публичные «константы», которые могут измениться, — это static readonly.

public const double Pi = 3.14159;                    // вшивается при компиляции
public static readonly HttpClient Client = new();    // инициализация в рантайме
public readonly int _retries;                         // задаётся в конструкторе

static vs const — когда инициализируются?

Коротко: const — значение вшивается на этапе компиляции, существует как константа в метаданных, не требует экземпляра. static — живёт на уровне типа, инициализируется при первом обращении к типу (через статический конструктор или инициализатор).

Подробнее: - const работает только с примитивами и строками — потому что их значения известны компилятору. - static readonly — как const, но вычисляется в рантайме, подходит для любых типов. - Статический конструктор гарантированно выполнится один раз, до любого обращения к членам типа.

Подводные камни: versioning problem (см. раздел 1) — главный аргумент против public const в библиотеках. Статический конструктор не может принимать параметры и никогда не вызывается явно; исключение в нём превращается в TypeInitializationException.

public class Config
{
    public const    string AppName    = "MyApp";          // компиляция
    public static readonly DateTime  StartTime = DateTime.UtcNow;  // рантайм
    public readonly string InstanceId;                    // инит в конструкторе
    static Config() { /* один раз перед первым использованием */ }
    public Config() { InstanceId = Guid.NewGuid().ToString(); }
}

Что такое record и чем отличается от class?

Коротко: record — reference type с value-семантикой равенства: два record равны, если равны их свойства (у class — только если это один и тот же объект). Плюс из коробки: with-копирование, деконструкция, читаемый ToString().

Подробнее: позиционный синтаксис record Point(int X, int Y) генерирует конструктор, init-only свойства, Equals/GetHashCode. Идеален для DTO, команд/запросов в CQRS, immutable-моделей. Есть и record struct — то же, но value type.

Подводные камни: record — это class (если не сказано record struct), передаётся по ссылке. with создаёт поверхностную копию: вложенные ссылочные объекты остаются общими. Для EF-сущностей record обычно не берут: у сущности идентичность по Id, а не по значению полей.

public record CreateOrderCommand(int UserId, decimal Total);

var cmd  = new CreateOrderCommand(42, 100m);
var copy = cmd with { Total = 150m };     // новый объект, UserId скопирован
Console.WriteLine(cmd == copy);           // False — сравнение по значениям

Primary constructors (C# 12) — что это и чем отличаются от record?

Коротко: параметры конструктора пишутся прямо в объявлении класса: public class OrderService(IOrderRepo repo, ILogger<OrderService> log). Параметры доступны во всём теле класса — исчезает ритуал «поле + конструктор + присваивание», особенно для DI-сервисов.

Подробнее: компилятор захватывает параметр в скрытое поле, только если тот реально используется в теле. В отличие от record, primary constructor у обычного class не генерирует свойства, Equals/GetHashCode и деконструкцию — это просто компактный синтаксис конструктора.

Подводные камни: захваченный параметр — изменяемый, пометить его readonly нельзя, и снаружи он не виден (это не свойство). Нужно readonly-поле — объяви явно и присвой из параметра. Интервьюер может показать такой код и спросить «что это»; кстати, почти все примеры в этом файле написаны именно так.

// C# 12: primary constructor
public class ReviewService(IReviewRepo repo, ILogger<ReviewService> log)
{
    public async Task<Review?> GetAsync(int id)
    {
        log.LogInformation("Загружаем отзыв {Id}", id);
        return await repo.FindAsync(id);   // repo захвачен компилятором в скрытое поле
    }
}

enum — что это и особенности

Коротко: enum — набор именованных целочисленных констант. По умолчанию тип — int, значения начинаются с 0 и инкрементируются.

Подробнее: Базовый тип можно задать: enum Status : byte. Флаговый enum ([Flags]) позволяет комбинировать через битовые операции: Permission.Read | Permission.Write.

public enum OrderStatus { Pending = 0, Paid, Shipped, Cancelled }

[Flags]
public enum Permission { None = 0, Read = 1, Write = 2, Admin = 4 }
var p = Permission.Read | Permission.Write;   // = 3
bool canRead = (p & Permission.Read) != 0;   // true

Подводные камни: (OrderStatus)999 компилируется и не бросает исключение — можно получить невалидный enum. Перед использованием: Enum.IsDefined(typeof(OrderStatus), value). Для хранения в EF Core лучше конвертить в строку (HasConversion<string>()) — БД останется читаемой при рефакторинге. Enum не может реализовывать интерфейсы (только extension methods могут добавить поведение).

Зачем нужны generics?

Коротко: обобщения дают типобезопасность и переиспользование кода без приведения типов и без boxing: List<int> хранит именно int, ошибки ловятся на компиляции, а не в рантайме.

Подробнее: constraints ограничивают параметр типа: where T : class, where T : IComparable<T>, where T : new(). Это позволяет внутри generic-кода вызывать методы T. Generic-методы, классы и интерфейсы — база всех коллекций, LINQ, DI-контейнера.

Подводные камни: для value types CLR генерирует отдельную специализацию кода — поэтому List<int> работает без boxing, в отличие от старого ArrayList.

public T FirstOrCreate<T>(List<T> list) where T : new()
    => list.Count > 0 ? list[0] : new T();

Что такое ковариантность и контравариантность?new

Коротко: Это правила, по которым обобщённый тип может подставляться вместо родственного. Ковариантность (out, «наследник вместо базового») позволяет IEnumerable<Dog> использовать как IEnumerable<Animal> — тип только возвращается. Контравариантность (in, «базовый вместо наследника») позволяет Action<Animal> использовать как Action<Dog> — тип только принимается.

Подробнее: запомнить логично, а не зубрить: если тип выходит наружу (out), сужение безопасно — любая собака и есть животное. Если тип принимается внутрь (in), безопасно расширение — обработчик, умеющий работать с любым животным, справится и с собакой. Поэтому out T можно ставить только на возвращаемые позиции, а in T — только на параметры; компилятор это проверяет. В BCL так объявлены IEnumerable<out T>, IReadOnlyList<out T>, Func<in T, out TResult>, Action<in T>, IComparer<in T>.

Подводные камни: (1) Вариантность работает только для интерфейсов и делегатов, и только для ссылочных типов: IEnumerable<int> в IEnumerable<object> не превратится — там нужен боксинг. (2) List<Dog> не конвертируется в List<Animal>: список позволяет и читать, и писать, а значит инвариантен — иначе можно было бы положить кошку в список собак. (3) Массивы в C# ковариантны исторически и небезопасно: Animal[] a = new Dog[1]; a[0] = new Cat(); скомпилируется, но упадёт в рантайме с ArrayTypeMismatchException — хороший пример, чтобы показать понимание.

IEnumerable<Dog> dogs = new List<Dog>();
IEnumerable<Animal> animals = dogs;      // ✅ ковариантность (out T)

Action<Animal> feedAny = a => a.Feed();
Action<Dog> feedDog = feedAny;           // ✅ контравариантность (in T)

List<Animal> list = new List<Dog>();     // ❌ List<T> инвариантен

Рефлексия — что это и как использовать?

Коротко: Механизм инспекции и динамической работы с типами в рантайме: получить тип объекта, список его полей/методов/атрибутов, создать экземпляр или вызвать метод по имени-строке.

Подробнее: Точка входа — Type через typeof(T), obj.GetType() или Type.GetType("FullName"). Использования: DI-контейнеры (находят все конструкторы), ORM (маппинг колонок на свойства), сериализаторы (JSON, XML), тестовые фреймворки (атрибуты [Fact], private-поля), source generators (замена рефлексии на компиляционный этап).

var type = typeof(Order);
var props = type.GetProperties();                   // все свойства
var method = type.GetMethod("Validate");
var instance = Activator.CreateInstance(type);      // new Order() через рефлексию
method?.Invoke(instance, null);                     // вызов метода по имени

// Чтение атрибутов
if (type.GetCustomAttribute<SerializableAttribute>() is not null)
    Console.WriteLine("Тип сериализуем");

Подводные камни: Рефлексия медленнее прямого вызова (нет JIT-оптимизации); в горячем коде кэшируй результаты MethodInfo/PropertyInfo. В .NET 8 Source Generators и [GeneratedCode] позволяют генерировать типо-безопасный код на этапе компиляции вместо рефлексии — тренд в современном .NET.

Атрибуты в C# — что это и для чего?

Коротко: Атрибут — метаданные, прикреплённые к типу/методу/свойству и читаемые в рантайме через рефлексию или compile-time через source generators. Позволяют декларативно задавать поведение.

Подробнее: Атрибут — класс, наследующий System.Attribute. Параметр AttributeTargets задаёт, к чему можно применять. Примеры из жизни: - [Required], [Range], [EmailAddress] — валидация DataAnnotations. - [Authorize], [HttpGet], [FromBody] — ASP.NET Core роутинг. - [JsonPropertyName], [JsonIgnore] — сериализация. - [Fact], [Theory] — тестовые фреймворки. - [Obsolete] — предупреждение об устаревшем API.

[AttributeUsage(AttributeTargets.Method, AllowMultiple = false)]
public class AuditAttribute : Attribute
{
    public string Action { get; }
    public AuditAttribute(string action) => Action = action;
}

[Audit("DeleteUser")]
public void DeleteUser(int id) { ... }

// Чтение через рефлексию
var method = typeof(UserService).GetMethod(nameof(DeleteUser));
var attr   = method?.GetCustomAttribute<AuditAttribute>();
Console.WriteLine(attr?.Action);  // "DeleteUser"

ООП и SOLID

0/16

Что такое ООП и зачем оно нужно?

Коротко: ООП — парадигма программирования, где программа моделируется через объекты, объединяющие данные (поля) и поведение (методы). Даёт переиспользование кода, снижает сложность через абстракцию и упрощает поддержку больших систем.

Подробнее: ООП появилось как ответ на растущую сложность программ: разбить систему на самодостаточные «вещи» (объекты), которые взаимодействуют через чёткие интерфейсы, проще, чем держать одну длинную процедуру. Концепция близка к реальному миру: автомобиль — объект с состоянием (скорость, уровень топлива) и поведением (поехать, затормозить).

Подводные камни: ООП — не серебряная пуля. Для маленьких утилит или трансформаций данных функциональный или процедурный подход бывает проще. Умение выбрать парадигму под задачу ценится больше, чем «ООП везде».

В чём разница между процедурным и ООП-программированием?

Коротко: В процедурном коде — функции, работающие с данными, данные и логика разделены. В ООП — объекты сами хранят своё состояние и поведение вместе.

Подробнее:

Процедурное ООП
Данные и логика Разделены Инкапсулированы в объект
Переиспользование Функции Наследование, композиция
Сложность Растёт линейно Управляется через абстракции
Примеры C, Pascal C#, Java, Python

Подводные камни: C# поддерживает оба стиля: можно написать процедурный код в статических методах. Функциональные фичи (LINQ, лямбды) тоже встроены. Современный C# — мультипарадигменный язык.

Четыре принципа ООП простыми словами★

Коротко: инкапсуляция, наследование, полиморфизм, абстракция.

Подробнее: - Инкапсуляция — скрываем внутреннее устройство, наружу — только нужные методы/свойства. Поля private, доступ через свойства; невозможно привести объект в невалидное состояние извне. - Наследование — класс строится на основе другого и переиспользует его код. Отношение «является» (Dog is an Animal). - Полиморфизм — работа с разными типами через общий контракт: клиент вызывает IPayment.Pay(), не зная, карта это или PayPal. Виды: через наследование/интерфейсы (runtime) и перегрузка методов (compile-time). - Абстракция — выделяем существенное, прячем детали: интерфейс IEmailSender описывает «что», а не «как».

Подводные камни: на follow-up «какой принцип главный на практике?» хороший ответ — инкапсуляция: она защищает инварианты. И добавить: «наследованием стараюсь не злоупотреблять, предпочитаю композицию» — это мостик к следующим вопросам.

SOLID — расшифруй и приведи примеры★

Коротко: пять принципов проектирования, снижающих связность и упрощающих изменения.

Подробнее: - S — Single Responsibility: у класса одна причина для изменения. OrderService не должен сам форматировать email и писать в файл лога. - O — Open/Closed: открыт для расширения, закрыт для модификации. Новый способ расчёта скидки = новый класс-стратегия, а не очередной else if внутри старого метода. - L — Liskov Substitution: подтип должен подставляться вместо базового типа без сюрпризов. Классическое нарушение: Square : Rectangle, где сеттер Width ломает ожидания по Height. - I — Interface Segregation: много маленьких интерфейсов лучше одного «толстого». Если реализация вынуждена кидать NotImplementedException — интерфейс распилен неправильно. - D — Dependency Inversion: зависим от абстракций, а не от конкретики. Сервис принимает IOrderRepository в конструктор, а не создаёт new SqlOrderRepository() внутри.

Подводные камни: не пересказывай определения без примеров — интервьюер почти всегда просит «покажи на коде из своего опыта». Подготовь по одному примеру из своего проекта (в Sentio: стратегии анализа тональности → O, интерфейсы в Application, реализации в Infrastructure → D).

Интерфейс vs абстрактный класс★

Коротко: интерфейс — чистый контракт «что умеет тип», класс может реализовать много интерфейсов. Абстрактный класс — общая база с состоянием и частичной реализацией, наследовать можно только один.

Подробнее: абстрактный класс выбирают, когда есть общие поля/логика для семейства классов (Template Method: базовый алгоритм с абстрактными шагами). Интерфейс — когда нужен контракт для несвязанных типов и подмена в DI/тестах.

Подводные камни: с C# 8 интерфейсы могут иметь default-реализации методов — граница размылась, но ключевое отличие осталось: интерфейс не может иметь состояния (полей). На вопрос «что выбрать?» практичный ответ: по умолчанию интерфейс; абстрактный класс — когда реально есть общий код и состояние.

Интерфейсы: в чём разница с наследованием классов? Можно ли private метод?

Коротко: Класс может наследовать один базовый класс, но реализовывать много интерфейсов. Интерфейс — контракт без состояния; класс — и контракт, и данные, и частичная реализация.

Подробнее: С C# 8 интерфейсы могут содержать default implementations (методы с телом) и обычные static-члены с телом; с C# 11 — ещё и static abstract/static virtual (фундамент generic math: INumber<T>). private методы в интерфейсе — разрешены с C# 8, но только для поддержки default-реализаций: они не являются частью публичного контракта и не видны реализующему классу.

public interface IProcessor
{
    void Process(string data);

    void ProcessBatch(IEnumerable<string> items)  // default implementation
    {
        foreach (var item in items) Process(item);
    }

    private static void Validate(string data)     // private — вспомогательный
    {
        if (string.IsNullOrEmpty(data)) throw new ArgumentException();
    }
}

Подводные камни: Реализующий класс не видит private-метод интерфейса — только сам интерфейс может его вызвать. Explicit interface implementation (явная реализация) скрывает метод: вызвать его можно только через ссылку на интерфейс, что позволяет реализовать два интерфейса с одинаковым именем метода по-разному.

Абстрактный класс: может ли абстрактный метод иметь реализацию? Чем abstract отличается от virtual?

Коротко: Абстрактный метод — только объявление, тело запрещено, наследники обязаны переопределить. Virtual — имеет реализацию по умолчанию, наследники могут переопределить.

Подробнее: Оба обеспечивают динамический полиморфизм. Abstract — более строгий контракт: «каждый наследник ДОЛЖЕН реализовать это». Virtual — гибкость: «вот реализация по умолчанию, при желании переопредели».

public abstract class Report
{
    public abstract string GetTitle();             // нет тела — обязан переопределить
    public virtual string GetFooter() => "© 2026"; // есть тело — можно оставить как есть

    public void Generate()  // конкретный метод — Template Method
    {
        Console.WriteLine(GetTitle());
        Console.WriteLine(GetFooter());
    }
}

Подводные камни: Абстрактный класс может содержать как абстрактные, так и обычные методы. Смешение конкретного кода с абстрактным контрактом — паттерн Template Method. abstract метод автоматически подразумевает virtual — отдельно virtual писать не нужно.

virtual / override / new — в чём разница?

Коротко: virtual разрешает переопределение метода в наследнике, override переопределяет — вызов идёт по фактическому типу объекта. new скрывает метод базового класса — вызов зависит от типа ссылки.

Подводные камни: классическая задачка-ловушка на собеседовании — см. код. С override через базовую ссылку вызовется метод наследника, с new — метод базового класса. Method hiding почти всегда запах дизайна; в реальном коде нужен override.

class Animal { public virtual string Voice() => "..."; }
class Dog : Animal { public override string Voice() => "Гав"; }
class Cat : Animal { public new string Voice() => "Мяу"; }

Animal a1 = new Dog();
Animal a2 = new Cat();
a1.Voice();   // "Гав"  — override: смотрим на объект
a2.Voice();   // "..."  — new: смотрим на тип ссылки (Animal)

Перегрузка и переопределение методов — коротко

Коротко: Overloading (перегрузка) — несколько методов с одним именем, но разными сигнатурами (типы/количество параметров). Overriding (переопределение) — подкласс меняет реализацию virtual-метода базового через override. Разные задачи: первое — удобство API, второе — полиморфизм.

Подводные камни: Возвращаемый тип не участвует в разрешении перегрузки — void Foo() и int Foo() не компилируются вместе. С C# 9 тип возврата при переопределении может быть ковариантным (covariant return types): override вправе вернуть более конкретный тип, чем базовый метод.

Типы наследования: какие бывают?

Коротко: Одиночное, многоуровневое, иерархическое — базовые. Множественное (через несколько классов напрямую) в C# запрещено, но доступно через интерфейсы. Гибридное = комбинация нескольких видов.

Подробнее: - Одиночное (Single): Dog : Animal — один наследник, один предок. - Многоуровневое (Multilevel): Puppy : Dog : Animal — цепочка. - Иерархическое (Hierarchical): от одного класса несколько: Dog : Animal, Cat : Animal. - Множественное (Multiple): один класс наследует несколько. В C# запрещено для классов — вместо этого несколько интерфейсов. - Гибридное (Hybrid): сочетание видов выше, чаще через интерфейсы.

Подводные камни: Запрет множественного наследования классов — осознанное решение во избежание Diamond Problem (ромбовидное наследование): если A и B оба наследуют Base и переопределяют один метод, а C наследует A и B — непонятно, какая реализация победит. Интерфейсы это решают через explicit implementation.

public interface ISwim { void Swim(); }
public interface IFly  { void Fly(); }
public class Duck : Animal, ISwim, IFly   // множественное — через интерфейсы
{
    public void Swim() => Console.WriteLine("Плыву");
    public void Fly()  => Console.WriteLine("Лечу");
}

Ограничения наследования в C#

Коротко: нельзя наследовать несколько классов; sealed class запрещает наследование вообще; конструкторы, деструкторы и static-члены не наследуются; private-члены недоступны в наследнике.

Подробнее: Правила доступа при наследовании: public и protected — наследуются, private — физически в классе есть, но недоступны из наследника напрямую. Именно для «открытого внутри иерархии, закрытого снаружи» существует protected.

Подводные камни: «Наследование — сильная связь». Менять базовый класс страшно: любое изменение сигнатуры ломает всех потомков (fragile base class problem). Поэтому принцип «предпочитай композицию наследованию».

Статический и динамический полиморфизм — в чём разница?

Коротко: Статический (compile-time) — перегрузка методов (overloading): компилятор сам выбирает нужный метод по сигнатуре вызова. Динамический (runtime) — переопределение (overriding) через virtual/override: нужный метод выбирается в рантайме по фактическому типу объекта.

Подробнее: - Статический: void Print(int x) и void Print(string x) — два метода с одним именем, разными параметрами. Вызов разрешается на этапе компиляции. - Динамический: Animal a = new Dog(); a.Voice() — какой Voice() вызовется, решается в рантайме через таблицу виртуальных методов (vtable).

Подводные камни: Операторы (+, ==) тоже перегружаются — это статический полиморфизм. Дженерики — ещё один вид статического полиморфизма: один шаблон кода для разных типов, специализации генерируются компилятором.

// Статический: сигнатура выбрана на компиляции
class Logger
{
    public void Log(string msg)  => Console.WriteLine($"[STR] {msg}");
    public void Log(int code)    => Console.WriteLine($"[INT] {code}");
}

// Динамический: метод выбран в рантайме
Animal a = new Dog();
a.Voice();   // "Гав", хотя тип ссылки Animal

Что такое upcasting и downcasting?

Коротко: Upcasting — приведение к базовому/интерфейсному типу: всегда безопасно, происходит неявно. Downcasting — приведение к производному типу: рискованно, может бросить InvalidCastException.

Подробнее: Паттерн безопасного downcasting — is / as: as возвращает null вместо исключения, is проверяет и опционально кастует через pattern matching.

Подводные камни: (Dog)animal бросит исключение, если объект на самом деле Cat. Использование as без проверки на null — та же проблема, просто с отложенным NullReferenceException. Pattern matching (if (animal is Dog dog)) — самый читаемый и безопасный вариант.

Animal animal = new Dog();     // upcasting — неявный, безопасен

// Downcasting — три способа:
var dog1 = (Dog)animal;                      // бросит, если не Dog
var dog2 = animal as Dog;                    // null если не Dog
if (animal is Dog dog3) dog3.Fetch();        // pattern matching — лучший вариант

Что такое конструктор? Типы конструкторов в C#

Коротко: Конструктор — специальный метод, вызываемый при создании объекта (new). Имя совпадает с именем класса, нет возвращаемого типа. Задача — инициализировать состояние объекта.

Типы: - Экземплярный (Instance) — обычный, вызывается при new. - Параметризованный — принимает аргументы для инициализации. - Без параметров (Default) — без аргументов; компилятор добавляет автоматически, если ни одного конструктора нет. - Статический (Static) — вызывается один раз при первом обращении к типу; инициализирует статические поля; нельзя вызвать вручную, не принимает параметров. - Копирующий — принимает объект того же типа и копирует поля; в C# нет встроенного, пишется вручную или через record with. - Private — запрещает создание объекта снаружи (Singleton, фабричный метод).

public class Order
{
    public static int TotalCreated { get; private set; }

    static Order() { TotalCreated = 0; }              // статический: один раз

    public Order(int id) { Id = id; TotalCreated++; } // параметризованный

    private Order() { }                                // private: запрет снаружи

    public int Id { get; }
}

Подводные камни: Если объявил хотя бы один конструктор — автоматический default не генерируется. Добавили параметризованный конструктор в класс-DTO — сломали код, который делал new Dto(). Особенность struct: default-конструктор без параметров нельзя объявить явно (до C# 10). Современная альтернатива конструкторам для DTO — required-свойства (C# 11): компилятор обязывает задать их в инициализаторе объекта.

Когда применять композицию вместо наследования?

Коротко: почти всегда, когда есть выбор. Композиция («имеет») гибче наследования («является»): поведение можно собирать из частей и менять в рантайме, зависимости легко мокать в тестах.

Подробнее: наследование жёстко связывает наследника с реализацией родителя — изменение базового класса ломает всех детей (fragile base class). Композиция + интерфейсы позволяют комбинировать поведение: закэшированный репозиторий = обычный репозиторий, обёрнутый в декоратор.

// Декоратор: добавляем кэширование, не трогая SqlProductRepo
public class CachedProductRepo(IProductRepo inner, IMemoryCache cache) : IProductRepo
{
    public async Task<Product?> GetAsync(int id) =>
        await cache.GetOrCreateAsync($"product:{id}", _ => inner.GetAsync(id));
}

Подводные камни: наследование оправдано, когда есть настоящая иерархия «является» + общий код: Exception → ValidationException, базовые Entity в DDD. Ответ «наследование никогда» — тоже неверен.

GetHashCode и Equals — как работают и почему важно оба?

Коротко: Equals определяет логическое равенство объектов. GetHashCode возвращает числовой хэш. Контракт: если a.Equals(b) == true, то a.GetHashCode() == b.GetHashCode(). Нарушение этого контракта ломает Dictionary и HashSet.

Подробнее: Dictionary сначала ищет по хэш-коду (быстро, O(1) bucket), затем проверяет Equals внутри bucket. Если переопределил Equals, но не GetHashCode — два «равных» объекта могут попасть в разные bucket'ы и не будут найдены.

public class Money
{
    public decimal Amount { get; }
    public string Currency { get; }
    public Money(decimal amount, string currency) => (Amount, Currency) = (amount, currency);

    public override bool Equals(object? obj) =>
        obj is Money other && Amount == other.Amount && Currency == other.Currency;

    public override int GetHashCode() =>
        HashCode.Combine(Amount, Currency);  // .NET Core: HashCode.Combine — лучший вариант
}

Основные принципы: хэш-код должен быть стабильным в течение жизни объекта (не меняться после добавления в коллекцию), детерминированным (один и тот же объект = один и тот же хэш), равномерно распределённым. HashCode.Combine(field1, field2, ...) из .NET Core реализует всё это за тебя.

Подводные камни: Не переопределяй GetHashCode для мутабельных объектов, если они используются как ключи: изменил объект → хэш изменился → словарь потерял запись. record автоматически генерирует Equals и GetHashCode по всем свойствам.

Коллекции и LINQ

Основные коллекции и их сложность операций★

Коротко: List<T> — динамический массив; Dictionary<K,V> — хэш-таблица «ключ→значение»; HashSet<T> — множество уникальных элементов; Queue<T>/Stack<T> — FIFO/LIFO.

Подробнее:

Как устроен List<T> изнутри и чем отличается от Array, LinkedList и ArrayList?new

Коротко: List<T> — обёртка над обычным массивом, который автоматически растёт. Array — фиксированный по размеру непрерывный блок памяти. LinkedList<T> — двусвязный список из узлов, разбросанных по куче. ArrayList — устаревшая нетипизированная коллекция из .NET 1.0, хранящая object.

Подробнее — как растёт List: внутри поля _items (массив) и _size (сколько занято). При Add, когда _size == _items.Length, выделяется новый массив вдвое больше (0 → 4 → 8 → 16…), старое содержимое копируется. Отсюда амортизированная сложность Add — O(1), но отдельная вставка с ресайзом стоит O(n). Если размер известен заранее — задавай new List<T>(capacity) и избегай перевыделений.

(2) LinkedList на практике почти всегда проигрывает List даже там, где по «бумажной» сложности должен выигрывать: обход по ссылкам убивает кэш процессора. Как работает Dictionary «под капотом»?

Коротко: Dictionary — хэш-таблица: ключ → GetHashCode → bucket (массив) → цепочка/открытая адресация для коллизий → Equals для точной проверки. Амортизированный O(1) для Get/Set/Contains.

Подробнее: .NET Dictionary делит массив на «buckets»; индекс bucket = hashCode % bucketsCount. При коллизии (два ключа → один bucket) записи сцепляются в цепочку (separate chaining, реализован через индексы в массиве entries, а не «настоящий» LinkedList). Resize происходит, когда массив entries заполнен целиком: новый размер — ближайшее простое число ≥ 2×, все ключи перехэшируются.

Подводные камни: Итерация по Dictionary не гарантирует порядок — используй SortedDictionary (сортировка по ключу) или generic OrderedDictionary<K,V> (.NET 9+, сохраняет порядок вставки). Чувствительность строковых ключей к регистру настраивается компаратором: new Dictionary<string,int>(StringComparer.OrdinalIgnoreCase). ConcurrentDictionary — потокобезопасная версия без внешних lock'ов.

Хэш-таблица: устройство и обработка коллизий

Коротко: Хэш-таблица отображает ключи на значения через хэш-функцию: index = hash(key) % capacity. Коллизия — два ключа дают один индекс. Два метода разрешения: chaining (список в ячейке) и open addressing (ищем следующую свободную ячейку).

Подробнее — в .NET Dictionary использует chaining: 1. key.GetHashCode() → число 2. abs(hash) % bucketCount → индекс bucket 3. Если bucket занят — цепочка Entry: сравниваем Equals до совпадения 4. Массив entries заполнен → resize (ближайшее простое ≥ 2×) и rehash. Порог ~72% (load factor 0.72) — это старая не-generic Hashtable; у Dictionary<K,V> его нет

Подводные камни: Плохая хэш-функция (все ключи дают 0) → все в одном bucket → O(N) вместо O(1). В .NET строки перемешиваются (randomised hash seed) при каждом запуске — нельзя полагаться на конкретное значение GetHashCode между запусками. Dictionary не потокобезопасен — ConcurrentDictionary для многопоточного кода.

Enumerator — что это и как работает?

Коротко: IEnumerator<T> — курсор для обхода коллекции. foreach — синтаксический сахар: компилятор вызывает GetEnumerator(), затем в цикле MoveNext(), читает Current.

// foreach разворачивается в:
var enumerator = list.GetEnumerator();
try
{
    while (enumerator.MoveNext())
    {
        var item = enumerator.Current;
        // тело цикла
    }
}
finally { enumerator.Dispose(); }

Подробнее: Для работы с foreach класс должен иметь метод GetEnumerator(), возвращающий объект с MoveNext() и Current — строгого наследования от IEnumerable<T> не требуется (duck typing). yield return делает создание энумераторов удобным — компилятор генерирует конечный автомат.

Подводные камни: Нельзя изменять коллекцию во время foreach — InvalidOperationException. IEnumerator одноразовый: после достижения конца MoveNext() возвращает false, сброс через Reset() не поддерживается большинством реализаций. Не путать IEnumerable (описание обходимой последовательности) и IEnumerator (конкретный курсор в процессе обхода).

Как работает yield return?

Коротко: yield return превращает метод в ленивый генератор последовательности: компилятор строит конечный автомат, и элементы вычисляются по одному по мере перечисления, а не все сразу.

Подробнее: полезно для стриминга больших объёмов (читать файл построчно, отдавать страницы из API) — в памяти находится один элемент, а не вся коллекция. yield break завершает последовательность.

Подводные камни: код до первого yield не выполнится, пока не начнётся перечисление — валидация аргументов «отложится» и исключение вылетит в неожиданном месте. И то же правило множественного перечисления: каждый foreach запускает генератор заново.

static IEnumerable<string> ReadLines(string path)
{
    using var reader = new StreamReader(path);
    while (reader.ReadLine() is { } line)
        yield return line;          // по одной строке, файл не грузится целиком
}

IEnumerable vs IQueryable — в чём разница?★

Коротко: IEnumerable<T> — выполнение в памяти (LINQ to Objects), принимает делегаты Func<>. IQueryable<T> — дерево выражений Expression<Func<>>, которое провайдер (EF Core) транслирует в SQL и выполняет на стороне БД.

Подробнее: пока цепочка — IQueryable, фильтры/сортировки/проекции уедут в SQL. После AsEnumerable() / ToList() всё дальнейшее выполняется в памяти приложения.

Подводные камни: главная ловушка — ранний ToList(): db.Orders.ToList().Where(o => o.Total > 100) вытянет всю таблицу в память и отфильтрует уже там. EF Core 3+ бросает исключение, если выражение нельзя перевести в SQL (например, вызов своего C#-метода внутри Where) — это защита от тихой client-side evaluation.

// SQL: SELECT ... WHERE Total > 100 — фильтр в БД ✅
var q1 = db.Orders.Where(o => o.Total > 100).ToList();

// Вся таблица в память, фильтр в C# ❌
var q2 = db.Orders.AsEnumerable().Where(o => o.Total > 100).ToList();

Что такое deferred execution (отложенное выполнение)?

Коротко: LINQ-запрос — это описание, а не результат. Он выполняется только при перечислении: foreach, ToList(), Count(), First().

Подробнее: операторы делятся на отложенные (Where, Select, OrderBy — строят запрос) и немедленные (ToList, ToArray, Count, Sum — материализуют). До материализации запрос можно достраивать условно — так удобно собирать фильтры.

Подводные камни: повторное перечисление = повторное выполнение. Для IQueryable это два запроса к БД; для IEnumerable поверх yield — повторный прогон логики. Если результат нужен несколько раз — материализуй один раз в ToList(). Вторая ловушка — захват переменной цикла в лямбду: запрос увидит её последнее значение на момент выполнения.

var query = db.Products.Where(p => p.IsActive);   // SQL ещё не выполнен
if (onlyCheap) query = query.Where(p => p.Price < 100);
var list = await query.ToListAsync();             // выполнился один итоговый SQL

First vs FirstOrDefault vs Single vs SingleOrDefault

Коротко: First — первый элемент, исключение если пусто. FirstOrDefault — первый или default (null). Single — гарантирует ровно один, исключение если 0 или больше одного. SingleOrDefault — один или default, исключение если больше одного.

Подробнее: Single — это утверждение об инварианте: «по этому условию запись одна» (поиск по уникальному ключу). Если дубликат возможен по бизнес-логике — бери First + OrderBy.

Подводные камни: в EF Core Single генерирует SELECT TOP(2) — чтобы обнаружить нарушение уникальности, а не просто взять первую строку. После FirstOrDefault не забудь проверку на null (или бросай осмысленный NotFoundException).

LINQ: extension syntax vs query syntax

Коротко: Два синтаксических способа писать одно и то же: extension methods (цепочки .Where().Select()) и query syntax (похоже на SQL, from...where...select). Компилятор превращает оба в одно.

var orders = new[] { new Order(1, 100), new Order(2, 50) };

// Extension syntax (используется в 95% кода)
var paid = orders
    .Where(o => o.Total > 75)
    .Select(o => new { o.Id, o.Total })
    .OrderByDescending(o => o.Total)
    .ToList();

// Query syntax (удобна для join'ов)
var result = from o in orders
             where o.Total > 75
             orderby o.Total descending
             select new { o.Id, o.Total };

Подводные камни: Query syntax не покрывает всё — Aggregate, ToList, Skip/Take — только через extension. Соответственно их часто смешивают: (from o in orders where o.Total > 75 select o).Take(10). Prefer extension syntax — он более читаем в больших командах, лучше поддерживается IDE.

Делегаты и события — что это и зачем?

Коротко: делегат — тип, представляющий ссылку на метод с определённой сигнатурой; можно передавать методы как параметры. Событие (event) — обёртка над делегатом, которая снаружи разрешает только подписку += и отписку -=, но не вызов и не перезапись.

Подробнее: в 95% случаев пишут не свои делегаты, а стандартные: Action<T> (ничего не возвращает), Func<T, TResult> (возвращает), Predicate<T> (возвращает bool). Лямбды — краткий синтаксис создания делегатов; на них построен весь LINQ.

Подводные камни: подписка на событие — скрытая ссылка: если короткоживущий объект подписался на событие долгоживущего и не отписался, GC не сможет его собрать (утечка). Вызов события — потокобезопасно через ?.Invoke.

public class OrderService
{
    public event Action<int>? OrderCreated;
    public void Create(int id) => OrderCreated?.Invoke(id);
}

Делегаты: Action, Func, Predicate — в чём разница? Как создать?

Коротко: Action<T> — делегат без возвращаемого значения (void). Func<T, TResult> — возвращает TResult. Predicate<T> — возвращает bool (частный случай Func<T, bool>).

Подробнее: Делегат объявляется как тип, инстанциируется присваиванием метода или лямбды. Multicast: к одному делегату можно добавить несколько методов через +=.

// Объявление своего делегата
public delegate int Transformer(int x);

// Использование готовых
Action<string>    log     = Console.WriteLine;          // void
Func<int, int>    square  = x => x * x;                // возвращает int
Predicate<string> isEmpty = string.IsNullOrEmpty;       // bool

// Multicast
Action greet = () => Console.Write("Hello ");
greet += () => Console.WriteLine("World");
greet();  // "Hello World"

Подводные камни: Multicast-делегат при исключении в одном из вызовов останавливается — остальные не вызываются. Если нужно вызвать всех — перебирай GetInvocationList() вручную. event = делегат + ограничения (+=/-= снаружи, Invoke — только изнутри).

В чём разница между Action и event Action?

Коротко: Публичный Action-делегат снаружи можно вызвать (obj.OnData("x")), перезаписать (obj.OnData = null) или подписаться. event — только подписка/отписка: внешний код не может вызвать событие или обнулить всех подписчиков. Это инкапсуляция.

public class DataFeed
{
    public Action<string>? OnData;          // поле-делегат: ЛЮБОЙ может вызвать
    public event Action<string>? DataArrived;  // event: только += и -=

    private void Receive(string data)
    {
        OnData?.Invoke(data);               // оба можно вызвать изнутри
        DataArrived?.Invoke(data);
    }
}

var feed = new DataFeed();
feed.OnData?.Invoke("test");               // ✅ внешний вызов работает
feed.DataArrived?.Invoke("test");          // ❌ compile error

Подводные камни: Для отписки нужно хранить ту же лямбду/метод: event += handler; ...; event -= handler;. Лямбды — разные объекты при каждом создании, поэтому event -= () => ... не отпишется. Хранить ссылку на handler-переменную — обязательно.

Что содержит обработчик события и как правильно объявлять события?new

Коротко: По соглашению .NET обработчик события имеет сигнатуру (object? sender, TEventArgs e): sender — кто вызвал событие, e — данные события. Для этого есть готовые делегаты EventHandler и EventHandler<TEventArgs>, свои делегаты объявлять почти никогда не нужно.

Подробнее: зачем это соглашение: один метод-обработчик можно подписать на несколько источников и различать их по sender, а все данные передавать одним объектом e — так сигнатуру можно расширять новыми полями, не ломая подписчиков. Вызывают событие через защищённый метод OnSomething, чтобы наследники могли переопределить поведение. Проверка ?.Invoke(...) обязательна: если подписчиков нет, поле события равно null.

Подводные камни: (1) Утечка памяти через события — самый частый follow-up: издатель держит ссылку на подписчика, и пока живёт издатель, подписчик не соберётся GC. Лечится отпиской (-=) в Dispose. (2) Исключение в одном обработчике прерывает вызов остальных. (3) event отличается от обычного поля-делегата тем, что снаружи доступны только += и -=: подписчик не может ни обнулить список, ни вызвать событие. (4) В многопоточном коде handler?.Invoke() пишут через локальную копию — ?. уже делает это безопасно.

public class OrderPaidEventArgs(Guid orderId, decimal amount) : EventArgs
{
    public Guid OrderId { get; } = orderId;
    public decimal Amount { get; } = amount;
}

public class OrderService
{
    public event EventHandler<OrderPaidEventArgs>? OrderPaid;

    protected virtual void OnOrderPaid(OrderPaidEventArgs e) => OrderPaid?.Invoke(this, e);

    public void Pay(Guid id, decimal amount)
    {
        // ... логика оплаты
        OnOrderPaid(new OrderPaidEventArgs(id, amount));
    }
}

// подписка и обязательная отписка
service.OrderPaid += Handle;
service.OrderPaid -= Handle;    // иначе подписчик не соберётся GC

Что такое замыкание (closure)?

Коротко: Замыкание — функция (лямбда/делегат), которая «захватывает» переменные из внешней области видимости и может обращаться к ним даже после того, как внешняя функция завершилась.

Подробнее: Компилятор создаёт скрытый класс, хранящий захваченные переменные как поля, — лямбда превращается в метод этого класса. Захватывается переменная, а не значение.

// Пример 1: захват переменной
int multiplier = 3;
Func<int, int> triple = x => x * multiplier;  // multiplier захвачен
multiplier = 10;
Console.WriteLine(triple(5));  // 50! не 15 — захвачена ПЕРЕМЕННАЯ

// Классическая ловушка в цикле
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
    actions.Add(() => Console.WriteLine(i));  // все захватили ОДНУ i

actions.ForEach(a => a());  // 3 3 3 — не 0 1 2!

// Исправление: копия переменной
for (int i = 0; i < 3; i++)
{
    int copy = i;
    actions.Add(() => Console.WriteLine(copy));  // каждый захватил свой copy
}

Подводные камни: Захваченные переменные продлевают время жизни объектов: лямбда ссылается на объект → GC не соберёт, пока жива лямбда. Это скрытый источник утечек памяти: событие подписано лямбдой с захватом this → подписчик держит объект живым.

async/await и многопоточность

0/7

Почему async/await важны для веб-приложений?★

Коротко: await не блокирует поток на время I/O (БД, HTTP, файлы) — поток возвращается в пул и обслуживает другие запросы. Итог: та же машина держит в разы больше одновременных запросов.

Подробнее: синхронный Query() держит поток «в заложниках» всё время ожидания ответа БД. При await QueryAsync() поток свободен; когда I/O завершится, продолжение метода выполнит любой поток из пула. Async — про масштабируемость при I/O, а не про скорость одного запроса.

Подводные камни: в ASP.NET Core нет SynchronizationContext (в отличие от старого ASP.NET), поэтому ConfigureAwait(false) в коде приложения обычно не нужен — но нужен в коде библиотек. Правило «async all the way»: не смешивать sync и async, пробрасывать async до контроллера. Для CPU-bound работы async сам по себе не помогает — там Task.Run или фоновая обработка.

Типичные ошибки с async/await★

Коротко: .Result / .Wait() (блокировки и дедлоки), async void (потерянные исключения), игнорирование CancellationToken, последовательный await независимых операций.

Подробнее: - .Result / .Wait() — блокируют поток; в средах с контекстом синхронизации (UI, старый ASP.NET) дают классический дедлок. Даже в ASP.NET Core это выжигает потоки пула → thread pool starvation под нагрузкой. - async void — исключение нельзя поймать снаружи, вызывающий не может дождаться завершения. Допустим только для обработчиков событий. Всегда async Task. - Независимые операции — не жди по очереди, запусти обе и жди вместе:

// Последовательно: время = t1 + t2 ❌
var user = await GetUserAsync(id);
var orders = await GetOrdersAsync(id);

// Параллельно: время = max(t1, t2) ✅
var userTask = GetUserAsync(id);
var ordersTask = GetOrdersAsync(id);
await Task.WhenAll(userTask, ordersTask);

Подводные камни: «забытый await» — DoAsync(); без await компилируется (с warning), но исключение потеряется, а вызывающий не дождётся результата (fire-and-forget по ошибке).

Task vs Thread — в чём разница?

Коротко: Thread — реальный поток ОС: дорогой (≈1 МБ стека), создаётся и уничтожается медленно. Task — легковесная абстракция «работа с результатом в будущем», планируется на ThreadPool; для I/O-задач вообще не держит поток во время ожидания.

Подробнее: руками new Thread() в бизнес-коде сегодня почти не создают. CPU-bound работу отправляют в Task.Run (возьмёт поток из пула), I/O-bound — через async API без Task.Run вовсе.

Подводные камни: «async = многопоточность» — неверно. Await на I/O может завершиться вообще без занятого потока (I/O completion ports); многопоточность — про параллельные вычисления, async — про неблокирующее ожидание. Разделить эти понятия в ответе — жирный плюс. Бонус-упоминание: ValueTask — оптимизация для методов, которые часто завершаются синхронно (например, чтение из кэша), экономит аллокацию Task; ограничение — await'ить его можно только один раз.

Какие есть способы запустить параллельную работу: Thread, ThreadPool, Task, Parallel?new

Коротко: Thread — ручное создание ОС-потока, дорого и почти никогда не нужно. ThreadPool — пул переиспользуемых потоков, чтобы не платить за создание. Task — абстракция над операцией, которая работает поверх пула и умеет возвращать результат, ошибки и отмену; это дефолт в современном коде. Parallel / PLINQ — для распараллеливания вычислений по данным.

Подробнее — что чем является: - Thread: ~1 МБ стека, дорогое создание. Оправдан только для долгоживущего выделенного потока с особыми настройками (например, IsBackground, свой приоритет, STA). - ThreadPool.QueueUserWorkItem: дёшево, но нет ни результата, ни обработки исключений — в прикладном коде вытеснен Task. - Task.Run: для CPU-bound работы, чтобы не блокировать текущий поток. Для I/O-bound (база, HTTP) Task.Run не нужен вообще — там await асинхронного API освобождает поток без всякого пула. - Parallel.For / Parallel.ForEach / PLINQ (AsParallel): data parallelism — одна и та же операция над множеством элементов; сам делит работу на партиции по числу ядер. С .NET 6 есть Parallel.ForEachAsync для асинхронных операций с ограничением параллелизма. - IHostedService / BackgroundService — правильный способ фоновой работы в ASP.NET Core вместо ручных потоков.

Подводные камни: (1) Главное различие, которое проверяют: параллелизм ≠ асинхронность. Параллелизм — занять несколько ядер работой; асинхронность — не держать поток, пока ждём внешний ответ. Task.Run(() => db.Query()) в ASP.NET Core — антипаттерн: поток всё равно занят, только теперь другой. (2) Внутри Parallel.For общее состояние надо защищать (Interlocked, lock) или собирать результат через локальные агрегаты. (3) У Parallel.ForEach нет смысла для I/O — используй Parallel.ForEachAsync с MaxDegreeOfParallelism.

// CPU-bound: вынести из потока запроса
var hash = await Task.Run(() => ComputeExpensiveHash(data), ct);

// I/O-bound: НЕ Task.Run — просто await
var user = await db.Users.FindAsync([id], ct);

// data parallelism с ограничением степени параллелизма
await Parallel.ForEachAsync(urls,
    new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct },
    async (url, token) => await httpClient.GetStringAsync(url, token));

Зачем нужен CancellationToken?

Коротко: это механизм кооперативной отмены: вызывающий сигнализирует «результат больше не нужен», а операция сама решает, где безопасно остановиться, — и не тратит ресурсы впустую.

Подробнее: в ASP.NET Core достаточно добавить параметр CancellationToken ct в action — фреймворк привяжет его к HttpContext.RequestAborted (клиент закрыл вкладку → токен отменён). Пробрасывай ct во все async-вызовы: EF (ToListAsync(ct)), HttpClient, задержки.

Подводные камни: токен нужно именно пробрасывать до конца — если проглотить его на полпути, отмена не сработает. Отменённая операция бросает OperationCanceledException — это нормальный поток управления, не логируй её как ошибку 500.

[HttpGet]
public async Task<IActionResult> Search(string q, CancellationToken ct)
{
    var items = await _db.Products
        .Where(p => p.Name.Contains(q))
        .ToListAsync(ct);            // клиент ушёл → запрос к БД отменится
    return Ok(items);
}

lock и race condition — базовое понимание

Коротко: race condition — результат зависит от порядка выполнения потоков (классика: два потока делают counter++, часть инкрементов теряется, потому что ++ — это read-modify-write). lock делает критическую секцию атомарной: внутрь заходит один поток за раз.

Подробнее: для простых счётчиков вместо lock — Interlocked.Increment(ref counter). Для словарей из нескольких потоков — ConcurrentDictionary. Объект блокировки — приватное readonly-поле.

Подводные камни: не делать lock(this) и lock на строках/публичных объектах — внешний код может заблокировать тот же объект и устроить дедлок. Внутри lock нельзя await (компилятор не даст) — для async-кода используется SemaphoreSlim(1,1) + WaitAsync. С .NET 9 / C# 13 есть выделенный тип System.Threading.Lock — lock с ним быстрее и семантически чище, чем блокировка на object.

private readonly object _sync = new();
private int _count;

public void Add()
{
    lock (_sync) { _count++; }
}

Семафор vs Mutex — в чём разница?

Коротко: Mutex — исключительный доступ для одного потока, и только тот поток, который взял Mutex, может его отпустить. Semaphore/SemaphoreSlim — считающий примитив: ограничивает N одновременных потоков, владелец не фиксирован.

Подробнее: - Mutex — ОС-примитив, работает между процессами (Named Mutex); дорогой. - SemaphoreSlim(1,1) — лёгкий управляемый семафор, замена lock там, где нужен await внутри критической секции. - lock = Monitor.Enter/Exit — быстрее Mutex, но работает только внутри процесса и не поддерживает async.

private readonly SemaphoreSlim _sem = new(1, 1);  // макс 1 поток = async-lock

public async Task<Data> GetOrLoadAsync(int id)
{
    await _sem.WaitAsync();          // async-friendly ожидание
    try
    {
        return _cache.TryGetValue(id, out var data)
            ? data
            : _cache[id] = await _repo.LoadAsync(id);
    }
    finally { _sem.Release(); }
}

Подводные камни: SemaphoreSlim(N, N) с N>1 — дроссель: ограничить число параллельных HTTP-запросов к внешнему API. Mutex отпускать ОБЯЗАТЕЛЬНО в том же потоке; если поток умер не отпустив — AbandonedMutexException у ожидающих.

Что такое middleware и зачем оно нужно?★

Коротко: middleware — компоненты конвейера обработки HTTP-запроса. Каждый получает HttpContext и делегат next; может отработать до следующего (аутентификация), после (логирование времени ответа) или вернуть ответ сразу, не пуская запрос дальше (short-circuit).

Подробнее: запрос проходит цепочку сверху вниз, ответ — обратно снизу вверх (луковица). Типовой pipeline: ExceptionHandler → HTTPS redirect → Static files → Routing → CORS → Authentication → Authorization → Endpoints.

Подводные камни: порядок регистрации критичен: UseAuthentication до UseAuthorization, UseRouting до того и другого, обработчик исключений — самым первым (чтобы ловить ошибки всех нижестоящих). Перепутанный порядок — классический баг «авторизация не работает».

Как написать свой middleware?

Коротко: класс с конструктором, принимающим RequestDelegate next, и методом InvokeAsync(HttpContext); регистрируется через app.UseMiddleware<T>().

public class TimingMiddleware(RequestDelegate next, ILogger<TimingMiddleware> log)
{
    public async Task InvokeAsync(HttpContext ctx)
    {
        var sw = Stopwatch.StartNew();
        await next(ctx);                      // передаём дальше по конвейеру
        sw.Stop();
        log.LogInformation("{Path} → {Code} за {Ms} мс",
            ctx.Request.Path, ctx.Response.StatusCode, sw.ElapsedMilliseconds);
    }
}
// Program.cs:
app.UseMiddleware<TimingMiddleware>();

Подводные камни: middleware создаётся один раз на всё приложение (по сути singleton) — Scoped-зависимости нельзя внедрять в конструктор, только параметрами в InvokeAsync (туда DI подставит их из scope текущего запроса). Для простых случаев есть inline-вариант: app.Use(async (ctx, next) => { ...; await next(); });

Что такое short-circuit в конвейере?

Коротко: middleware формирует ответ и не вызывает next() — запрос не идёт дальше по конвейеру. Так работают отдача статических файлов, ранний отказ по авторизации, rate limiting, ответы из кэша.

Подводные камни: после начала записи ответа (Response.HasStarted) менять статус-код и заголовки уже нельзя — исключение. Поэтому решение «пропускать или нет» принимается до вызова next.

Времена жизни в DI: Transient, Scoped, Singleton★

Коротко: Transient — новый экземпляр при каждом запросе из контейнера. Scoped — один экземпляр на HTTP-запрос. Singleton — один на всё время жизни приложения.

Подробнее: типовое применение: Singleton — конфигурация, кэш, HttpClient-обёртки, всё stateless и потокобезопасное; Scoped — DbContext, Unit of Work, текущий пользователь; Transient — лёгкие stateless-сервисы.

Подводные камни: captive dependency — главная ловушка: Scoped-сервис, внедрённый в Singleton, «застревает» в нём навсегда → все запросы делят один DbContext → падения и грязные данные. В Development контейнер валидирует скоупы и бросит InvalidOperationException, в Production по умолчанию — просто молча живёт баг. Если Singleton'у нужен Scoped — внедряй IServiceScopeFactory и создавай scope вручную (типовая история для background-джобов, в т.ч. Quartz).

builder.Services.AddSingleton<ICacheService, MemoryCacheService>();
builder.Services.AddScoped<IOrderService, OrderService>();     // живёт запрос
builder.Services.AddTransient<IEmailBuilder, EmailBuilder>();  // каждый resolve — новый

Authentication vs Authorization — в чём разница?★

Коротко: Аутентификация — «кто ты?»: проверка личности и построение ClaimsPrincipal из cookie/JWT. Авторизация — «что тебе можно?»: проверка прав уже известного пользователя (роли, политики, claims). Сначала всегда AuthN, потом AuthZ.

Подробнее: аутентификация настраивается схемами (AddAuthentication().AddJwtBearer(...)) и выполняется в UseAuthentication — он читает токен и наполняет HttpContext.User. Авторизация — [Authorize], [Authorize(Roles = "Admin")], [Authorize(Policy = "CanExport")]; политики собираются из требований к claims.

Подводные камни: прямое следствие для HTTP-кодов: 401 Unauthorized = не прошёл аутентификацию (нет/просрочен токен), 403 Forbidden = аутентифицирован, но прав не хватает. Название кода 401 «Unauthorized» исторически вводит в заблуждение — на собеседовании это любят. И порядок в Program.cs: UseAuthentication() строго до UseAuthorization().

[Authorize]                          // любой аутентифицированный
[HttpGet("me")] public IActionResult Me() => Ok(User.Identity!.Name);

[Authorize(Roles = "Admin")]         // только роль Admin
[HttpDelete("{id}")] public IActionResult Delete(int id) => NoContent();

Как устроен JWT и как с ним работать?

Коротко: JWT — три части через точку: header.payload.signature. Header — алгоритм; payload — claims (sub, роли, exp); signature — подпись сервера. Сервер не хранит сессию: валидность проверяется по подписи и claims → stateless-аутентификация.

Подробнее: клиент шлёт токен в заголовке Authorization: Bearer <token>. Сервер валидирует подпись, издателя (issuer), аудиторию (audience) и срок (exp). Т.к. access-токен нельзя «отозвать», его делают короткоживущим (минуты) и вводят refresh-токен для продления.

Подводные камни: payload только закодирован Base64, но не зашифрован — любой может прочитать его на jwt.io. Никаких секретов в claims! Подпись гарантирует целостность (не подменили), а не секретность. Секретный ключ подписи — в секретах окружения, не в appsettings в git.

Фильтры (Filters) vs Middleware — когда что?

Коротко: middleware работает для всех запросов и ничего не знает про MVC. Фильтры — конвейер внутри MVC: выполняются после роутинга, знают про выбранный action, аргументы модели и ModelState.

Подробнее: порядок фильтров: Authorization → Resource → (model binding) → Action → Exception → Result. Нужен доступ к результату биндинга или атрибутная точечная настройка на контроллер/метод — фильтр. Сквозная логика для всего трафика (логирование, CORS, сжатие) — middleware.

Подводные камни: пример для ответа: валидация модели — action filter (нужен ModelState), а глобальный обработчик исключений чаще middleware — он поймает ошибки и вне MVC.

Model binding и валидация — как работают?

Коротко: биндинг собирает параметры action из частей запроса: [FromRoute], [FromQuery], [FromBody] (JSON), [FromForm], [FromHeader]. Валидация — атрибуты DataAnnotations ([Required], [Range], [EmailAddress]) заполняют ModelState.

Подробнее: с атрибутом [ApiController] невалидная модель автоматически возвращает 400 с ProblemDetails — руками ModelState.IsValid проверять не нужно. Для сложных правил (условная валидация, обращение к БД) популярна FluentValidation.

Подводные камни: [FromBody] может быть только один на action (тело читается один раз). Complex-типы по умолчанию биндятся из body в [ApiController], простые — из route/query; при неоднозначности укажи источник явно.

Options pattern: IOptions vs IOptionsSnapshot vs IOptionsMonitor

Коротко: типизированный доступ к конфигурации: секция appsettings биндится в POCO-класс и внедряется через DI, вместо разбросанных Configuration["Key"].

Подробнее: IOptions<T> — singleton, читается один раз при старте, изменения файла не видит. IOptionsSnapshot<T> — scoped, перечитывается на каждый запрос (видит reload). IOptionsMonitor<T> — singleton + CurrentValue и событие OnChange, можно использовать в singleton-сервисах.

Подводные камни: запросить IOptionsSnapshot внутри singleton — та же captive dependency (scoped в singleton) и исключение; в singleton бери IOptionsMonitor. Валидация конфигурации на старте: .AddOptions<T>().Bind(...).ValidateDataAnnotations().ValidateOnStart() — сломанный конфиг уронит приложение сразу, а не в проде на первом запросе.

REST: соглашения и коды статусов★

Коротко: ресурсы — существительные (/api/orders/42), действия — HTTP-методами. Ответы: 2xx успех, 4xx ошибка клиента, 5xx ошибка сервера.

Controllers (MVC) — классы с атрибутами и богатой инфраструктурой: фильтры, конвенции, model binding. Оба подхода полноценны и могут жить в одном приложении.

Подводные камни: «Minimal — только для маленьких проектов» — устаревший тезис: с группировкой по файлам и MapGroup они нормально масштабируются. Взвешенный ответ на собеседовании: «новый сервис начал бы с Minimal APIs + route groups; в существующем проекте следую принятому стилю».

IDistributedCache (Redis) — общий внешний кэш: переживает рестарты и делится между инстансами, но платишь сериализацией и сетевым хопом. HybridCache (.NET 9+) объединяет оба уровня: L1 в памяти + L2 в Redis, со stampede-защитой из коробки.

Подробнее: темы, которые всплывают на собеседовании: absolute vs sliding expiration; инвалидация; cache stampede — тысяча запросов одновременно промахнулись мимо кэша и все пошли в БД (решение — блокировка по ключу; HybridCache делает это сам).

Подводные камни: кэшируй материализованный результат (DTO, не IQueryable). Не клади в IMemoryCache изменяемые объекты, которые потом кто-то мутирует, — «испортишь» кэш для всех. И всегда задавай expiration: кэш без TTL — утечка памяти по расписанию.

// HybridCache (.NET 9+): GetOrCreateAsync со stampede-защитой
public class ProductService(HybridCache cache, AppDbContext db)
{
    public async Task<ProductDto?> GetAsync(int id, CancellationToken ct) =>
        await cache.GetOrCreateAsync($"product:{id}",
            async token => await db.Products
                .Where(p => p.Id == id)
                .Select(p => new ProductDto(p.Id, p.Name, p.Price))
                .FirstOrDefaultAsync(token),
            new HybridCacheEntryOptions { Expiration = TimeSpan.FromMinutes(5) },
            cancellationToken: ct);
}

Что делает AsNoTracking и когда его использовать?★

Коротко: отключает Change Tracker для возвращённых сущностей: EF не хранит их снимки и не следит за изменениями. Экономит память и CPU — стандарт для read-only сценариев: списки, отчёты, GET-эндпойнты.

Подробнее: по умолчанию EF снимает «слепок» каждой загруженной сущности, чтобы при SaveChanges() вычислить diff. Для чтения это чистые накладные расходы. Есть AsNoTrackingWithIdentityResolution — не трекает, но склеивает одинаковые сущности в графе (одна и та же строка = один объект).

Подводные камни: изменения нетрекаемой сущности SaveChanges() не увидит — придётся Update() (пометит все поля как изменённые) или заново загрузить с трекингом. Если проецируешь в DTO через Select, трекинга и так нет — AsNoTracking там избыточен, хоть и не вреден. Можно включить по умолчанию: UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking).

var products = await db.Products
    .AsNoTracking()
    .Where(p => p.IsActive)
    .ToListAsync(ct);

Что такое проблема N+1, как её обнаружить и решить?★

Коротко: N+1 — один запрос за списком из N сущностей и затем по отдельному запросу за связями каждой из них: итого N+1 запросов вместо одного-двух. Главный убийца производительности при работе с ORM.

Подробнее — как обнаружить: в логах EF Core видно множество одинаковых SELECT с разными параметрами. Инструменты: логирование EF (LogTo), query.ToQueryString(), MiniProfiler, план запроса в СУБД. Частая причина — lazy loading в цикле или обращение к навигации после материализации.

Решения: 1. Проекция в DTO через Select — лучший вариант для чтения: SQL заберёт ровно нужные поля, включая данные из связей, одним запросом. 2. Include/ThenInclude — жадная загрузка графа, когда нужны сами сущности. 3. AsSplitQuery() — для больших графов с несколькими коллекциями: вместо одного JOIN-монстра с декартовым взрывом строк EF выполнит несколько запросов.

// ❌ N+1: за категорией каждого продукта — отдельный запрос (lazy loading)
foreach (var p in await db.Products.ToListAsync())
    Console.WriteLine(p.Category.Name);

// ✅ Один SQL с JOIN, только нужные поля
var list = await db.Products
    .Where(p => p.IsActive)
    .Select(p => new ProductDto(p.Id, p.Name, p.Category.Name))
    .ToListAsync(ct);

Подводные камни: Include «на всякий случай» тянет лишние данные; глубокие Include с коллекциями раздувают результат (cartesian explosion) — либо SplitQuery, либо проекция.

Способы загрузки связанных данных: eager, lazy, explicit

Коротко: Eager — Include/ThenInclude, связи грузятся сразу вместе с запросом. Lazy — навигация подгружается при первом обращении (нужны virtual-свойства + UseLazyLoadingProxies). Explicit — вручную по требованию: db.Entry(order).Collection(o => o.Items).LoadAsync().

Подробнее: дефолт EF Core — никакой автозагрузки: не включил Include — навигация будет null/пустой. Это осознанное решение против случайных N+1.

Подводные камни: lazy loading — главный генератор N+1 (обращение к навигации в цикле) и сюрпризов «запрос к БД из геттера»; в веб-API его обычно не включают. Практичный выбор: чтение — проекция в DTO, изменение — Include ровно того, что нужно.

Состояния сущностей и Change Tracker

Коротко: каждая отслеживаемая сущность имеет состояние: Added, Unchanged, Modified, Deleted, Detached. SaveChanges() по этим состояниям генерирует INSERT/UPDATE/DELETE в одной транзакции.

Подробнее: загрузил сущность → Unchanged; изменил свойство → трекер сам пометит Modified (сравнением со снимком); Add() → Added; Remove() → Deleted. Detached — контекст про объект не знает (пришёл из API).

Подводные камни: Update(entity) на detached-объекте помечает все поля как изменённые — UPDATE перезапишет всё, включая то, что не менялось (риск затереть чужие изменения). Чище: загрузить сущность и поменять нужные поля, либо Attach + пометить конкретные свойства. Follow-up про конкурентность: optimistic concurrency через rowversion/xmin — при конфликте DbUpdateConcurrencyException.

Пагинация: Skip/Take vs keyset — в чём разница?

Коротко: классика — OrderBy + Skip((page-1)*size) + Take(size): просто, позволяет прыгать на любую страницу, но на больших смещениях медленно — БД всё равно проходит пропускаемые строки. Keyset (seek) — Where(x => x.Id > lastSeenId).Take(size): стабильно быстро на любой глубине, но только «вперёд/назад» по курсору.

Подробнее: Skip/Take дополнительно страдает от сдвига данных: вставили строку между запросами страниц — элемент задублируется или пропадёт. Keyset устойчив к этому и идеален для бесконечной ленты. Обязательное правило любой пагинации: детерминированный OrderBy (уникальный ключ или тай-брейкер по Id).

// Skip/Take — админка с номерами страниц
var page3 = await db.Orders.OrderBy(o => o.Id)
    .Skip(2 * 20).Take(20).AsNoTracking().ToListAsync(ct);

// Keyset — лента/бесконечный скролл
var next = await db.Orders.Where(o => o.Id > lastSeenId)
    .OrderBy(o => o.Id).Take(20).AsNoTracking().ToListAsync(ct);

Подводные камни: для UI с общим числом страниц нужен отдельный CountAsync — это второй запрос, кэшируй или показывай «~примерно». Keyset по неуникальному полю (дате) требует составного курсора: (CreatedAt, Id).

Bulk-операции: как массово обновить/удалить/вставить?

Коротко: EF по умолчанию работает посущностно — на тысячах строк это медленно (загрузка в память + отдельные команды). Для массовых операций: ExecuteUpdateAsync/ExecuteDeleteAsync (EF Core 7+) — SQL сразу в БД без загрузки сущностей; для гигантских вставок — SqlBulkCopy (SQL Server), COPY (PostgreSQL) или библиотеки типа EFCore.BulkExtensions.

// EF Core 7+: один UPDATE в БД, ничего не загружаем
await db.Orders
    .Where(o => o.Status == OrderStatus.Pending && o.CreatedAt < cutoff)
    .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, OrderStatus.Expired), ct);

Подводные камни: ExecuteUpdate/Delete обходит Change Tracker: уже отслеживаемые в контексте сущности останутся со старыми значениями; интерсепторы/события SaveChanges не сработают. Учитывай транзакции, FK и триггеры; при больших вставках индексы иногда выгоднее временно отключить и перестроить.

Миграции: как работают и как применять в production?

Коротко: миграция — код-описание изменения схемы, генерируется сравнением модели с последним снимком: dotnet ef migrations add AddOrderStatus, применение — dotnet ef database update. Миграции лежат в git — схема версионируется вместе с кодом.

Подробнее: в production варианты: (1) сгенерировать идемпотентный SQL-скрипт dotnet ef migrations script --idempotent и катить его на деплое (DBA может проревьюить); (2) dotnet ef database update шагом CI/CD; (3) context.Database.Migrate() при старте приложения — удобно, но опасно при нескольких инстансах (гонка за применение); (4) dotnet ef migrations bundle — самодостаточный исполняемый файл с миграциями, удобен в CI/CD без SDK на сервере.

Подводные камни: проверяй сгенерированный код миграции глазами — переименование свойства EF может понять как drop column + add column = потеря данных. Откат (Down) есть, но на проде надёжнее катить новую «исправляющую» миграцию вперёд.

Транзакции в EF Core

Коротко: один вызов SaveChanges() уже атомарен — все изменения уходят в БД в одной транзакции. Явная транзакция нужна, когда в одну атомарную операцию надо связать несколько SaveChanges или EF + сырой SQL.

await using var tx = await db.Database.BeginTransactionAsync(ct);
try
{
    db.Orders.Add(order);
    await db.SaveChangesAsync(ct);

    stock.Quantity -= order.Qty;
    await db.SaveChangesAsync(ct);

    await tx.CommitAsync(ct);
}
catch
{
    await tx.RollbackAsync(ct);
    throw;
}

Подводные камни: держи транзакции короткими и не делай внутри внешние HTTP-вызовы — блокировки в БД живут, пока транзакция открыта. Для «БД + отправка события в брокер» транзакции недостаточно — упомяни паттерн Outbox, это сильный ответ.

Время жизни DbContext — почему Scoped и что с фоновыми задачами?

Коротко: AddDbContext регистрирует контекст как Scoped: один экземпляр на HTTP-запрос. DbContext лёгкий, не потокобезопасный и рассчитан на короткую жизнь: создался → отработал запрос → умер вместе с накопленным трекингом.

Подробнее: Scoped идеально ложится на веб: все сервисы запроса делят один контекст и одну «единицу работы». Долгоживущий контекст = распухший Change Tracker, устаревшие данные в кэше первого уровня и утечки памяти.

Подводные камни: в background-задачах (IHostedService, Quartz) HTTP-scope нет — внедрять DbContext напрямую в singleton нельзя (captive dependency). Решения: IServiceScopeFactory.CreateScope() на каждую итерацию джоба или IDbContextFactory<T> (AddDbContextFactory) — фабрика сама создаёт короткоживущие контексты; второй вариант — стандарт для параллельной работы.

        await using var db = await factory.CreateDbContextAsync();

Индексы: clustered, nonclustered, composite, covering — что где ставить?★

Коротко: индекс — структура (обычно B-tree), ускоряющая поиск ценой замедления записи и места на диске. Clustered определяет физический порядок строк таблицы (один на таблицу, в SQL Server по умолчанию создаётся на PK); nonclustered — отдельные структуры со ссылками на строки, их может быть много.

Подробнее: - Composite (A, B) работает для фильтров по A и по A AND B, но не по одному B — порядок колонок решает (правило «левого префикса»). - Covering — через INCLUDE(колонки) индекс содержит всё, что нужно запросу, и таблица вообще не читается. - Что индексировать: колонки в WHERE/JOIN/ORDER BY, внешние ключи. Что не стоит: низкоселективные колонки (пол, флаг), очень часто обновляемые поля.

CREATE NONCLUSTERED INDEX IX_Orders_UserId_CreatedAt
ON dbo.Orders (UserId, CreatedAt DESC)
INCLUDE (TotalAmount);   -- covering: запрос по юзеру+дате с суммой обслужится из индекса

Подводные камни: функция над колонкой в WHERE (WHERE YEAR(CreatedAt) = 2026) отключает индекс — переписывай в диапазон (>= '2026-01-01' AND < '2027-01-01'). Как проверить работу индекса — план выполнения: Index Seek хорошо, Table/Index Scan на большой таблице — повод думать. В PostgreSQL кластерного индекса «в живую» нет — таблица heap, но принципы те же.

Виды JOIN и их отличия★

Коротко: INNER JOIN — только совпавшие строки обеих таблиц; LEFT JOIN — все строки левой + совпадения правой (иначе NULL); RIGHT — зеркально; FULL — все строки обеих сторон; CROSS — декартово произведение.

-- Все пользователи и число их заказов, включая тех, у кого заказов нет
SELECT u.Name, COUNT(o.Id) AS OrdersCount
FROM Users u
LEFT JOIN Orders o ON o.UserId = u.Id
GROUP BY u.Name;

Подводные камни: классика собеседований — условие на правую таблицу в WHERE превращает LEFT JOIN в INNER: WHERE o.Status = 'Paid' отбросит строки с NULL. Если нужно сохранить «левых без пары», условие переносится в ON: LEFT JOIN Orders o ON o.UserId = u.Id AND o.Status = 'Paid'. И помни: JOIN по неуникальному ключу размножает строки — отсюда «почему сумма удвоилась».

WHERE vs HAVING, порядок выполнения запроса

Коротко: WHERE фильтрует строки до группировки, HAVING — группы после агрегации. Условие на агрегат (COUNT, SUM) может стоять только в HAVING.

Подробнее: логический порядок выполнения: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Отсюда же ответ, почему алиас из SELECT нельзя использовать в WHERE.

SELECT UserId, SUM(Total) AS Spent
FROM Orders
WHERE Status = 'Paid'          -- сначала отсекаем строки (индексы работают тут)
GROUP BY UserId
HAVING SUM(Total) > 1000;      -- затем фильтруем готовые группы

Подводные камни: всё, что можно, фильтруй в WHERE, а не в HAVING — меньше строк дойдёт до группировки.

Транзакции и ACID

Коротко: транзакция — группа операций «всё или ничего». ACID: Atomicity — либо все операции, либо ни одной; Consistency — из валидного состояния в валидное (constraints не нарушены); Isolation — параллельные транзакции не видят промежуточных состояний друг друга; Durability — после COMMIT данные переживут сбой.

Подводные камни: канонический пример для ответа — перевод денег: списание + зачисление обязаны быть атомарными. Уточнение «Isolation на самом деле настраиваемая — есть уровни» — идеальный мостик к следующему вопросу.

Уровни изоляции транзакций и аномалии

Коротко: уровень изоляции — компромисс между корректностью и параллелизмом. Аномалии: dirty read (чтение незакоммиченного), non-repeatable read (строка изменилась между двумя чтениями), phantom read (появились новые строки под то же условие).

Подробнее:

Уровень Dirty Non-repeatable Phantom
Read Uncommitted возможно возможно возможно
Read Committed (default SQL Server и PostgreSQL) нет возможно возможно
Repeatable Read нет нет возможно*
Serializable нет нет нет

* в PostgreSQL Repeatable Read реализован через снапшоты и фантомов тоже не даёт.

Подводные камни: выше уровень — больше блокировок/конфликтов и меньше throughput; Serializable «на всякий случай» не берут. SQL Server имеет режим Read Committed Snapshot (RCSI) — читатели не блокируют писателей, читая версию строки; в PostgreSQL версионность (MVCC) — родное поведение.

Нормализация: 1NF, 2NF, 3NF — зачем и когда отступать?

Коротко: нормализация устраняет дублирование данных и аномалии обновления. 1NF — атомарные значения, без списков в ячейке; 2NF — нет зависимости от части составного ключа; 3NF — нет транзитивных зависимостей (неключевое поле не зависит от другого неключевого).

Подробнее: пример нарушения 3NF: в таблице Orders хранить CustomerCity — город зависит от CustomerId, а не от заказа; изменится город клиента — придётся обновлять все его заказы (аномалия обновления). Правильно: город в таблице Customers.

Подводные камни: для тяжёлого чтения осознанно денормализуют: дублируют поля, держат материализованные агрегаты — меньше JOIN'ов, быстрее выборки, но сложнее поддерживать согласованность. Формулировка на собеседовании: «проектирую в 3NF, денормализую точечно по результатам профилирования».

Из чего состоит HTTP-запрос?

Коротко: стартовая строка (METHOD PATH VERSION, напр. POST /api/upload HTTP/1.1), заголовки (Host, Content-Type, Authorization...), пустая строка, тело.

Подробнее: query string (после ?) уходит на сервер как часть пути; фрагмент (#...) остаётся в браузере и на сервер не передаётся. Тело — произвольные байты; как их интерпретировать, серверу говорит Content-Type. Ответ симметричен: статусная строка (HTTP/1.1 200 OK), заголовки, тело.

Подводные камни: follow-up «а GET может иметь тело?» — технически спецификация не запрещает, но семантики у него нет, и промежуточные узлы могут его отбросить; параметры GET передают в query string.

Методы HTTP и идемпотентность★

Коротко: идемпотентный метод — повтор запроса даёт тот же результат, что и один вызов. GET, PUT, DELETE, HEAD — идемпотентны; POST — нет (каждый вызов создаёт новый ресурс); PATCH — не гарантированно.

Подробнее: семантика: GET — читает (safe: без побочных эффектов), POST — создаёт/выполняет действие, PUT — полная замена ресурса по известному URI, PATCH — частичное обновление, DELETE — удаление (повторный DELETE вернёт 404, но состояние сервера то же — идемпотентно).

Подводные камни: зачем это на практике: сеть ненадёжна, клиенты и прокси ретраят идемпотентные запросы автоматически. Ретраить POST опасно — дубль заказа; решение: idempotency key (клиент шлёт уникальный ключ, сервер дедуплицирует). Этот ответ звучит очень зрело.

Почему по HTTP можно передавать и JSON, и картинки, и файлы?

Коротко: потому что тело HTTP — это просто последовательность байтов поверх TCP. Формат байтов описывает заголовок Content-Type: application/json, image/png, application/pdf — сервер и клиент договариваются об интерпретации, транспорту всё равно.

Подробнее: когда в одном запросе нужно и то и другое (метаданные + файл), используется multipart/form-data: тело делится на части разделителем boundary, у каждой части свои мини-заголовки (Content-Disposition, Content-Type).

POST /upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----X

------X
Content-Disposition: form-data; name="meta"
Content-Type: application/json

{"title":"Документ"}
------X
Content-Disposition: form-data; name="file"; filename="doc.pdf"
Content-Type: application/pdf

%PDF-1.4 ...
------X--

Как в ASP.NET Core принять файл и JSON-метаданные одновременно?

Коротко: IFormFile для файла + [FromForm] модель для полей — фреймворк сам разложит multipart/form-data.

[HttpPost("upload")]
public async Task<IActionResult> Upload([FromForm] UploadMeta meta, IFormFile file, CancellationToken ct)
{
    if (file is null || file.Length == 0) return BadRequest("Файл пуст");

    var safeName = Path.GetRandomFileName();               // не доверяем имени клиента!
    var path = Path.Combine(_storagePath, safeName);
    await using var fs = new FileStream(path, FileMode.Create);
    await file.CopyToAsync(fs, ct);
    return Ok(new { savedAs = safeName });
}

Подводные камни: (1) file.FileName приходит от клиента — не использовать его в путях (path traversal), генерируй своё имя и валидируй расширение/Content-Type. (2) Лимиты размера: [RequestSizeLimit], настройки Kestrel/FormOptions. (3) Большие файлы — стриминг, а не буферизация в память.

Base64 в JSON или multipart/form-data — что выбрать для файлов?

Коротко: base64 раздувает данные на ~33% и требует кодирования на обеих сторонах — терпимо для мелочи (иконка в конфиге), плохо для файлов. Стандарт — multipart/form-data или отдельный upload-эндпойнт.

Подробнее: для больших файлов и продакшн-нагрузок — загрузка напрямую в объектное хранилище (S3/Azure Blob) по pre-signed URL: API выдаёт временную подписанную ссылку, клиент грузит мимо сервера, серверу возвращается только ключ файла. Разгружает API и убирает лимиты тела запроса.

Что такое CORS и зачем настраивать?

Коротко: CORS — механизм браузера, ослабляющий same-origin policy: JS со страницы https://app.example по умолчанию не может читать ответы https://api.example, пока API явно не разрешит origin через заголовки Access-Control-Allow-*.

Подробнее: для «непростых» запросов (JSON, свои заголовки) браузер сначала шлёт preflight OPTIONS, и только получив разрешение — сам запрос. В ASP.NET Core: AddCors с политикой (origins, methods, headers) + UseCors в правильном месте конвейера (после UseRouting, до auth).

Подводные камни: CORS — защита пользователя браузера, а не API: Postman, curl и сервер-сервер запросы он не ограничивает; авторизация всё равно обязательна. AllowAnyOrigin вместе с credentials запрещён спецификацией — при куках перечисляй origins явно.

Чем HTTPS отличается от HTTP (на пальцах)?

Коротко: HTTPS = HTTP поверх TLS: трафик шифруется, сервер подтверждает подлинность сертификатом, данные защищены от прослушивания и подмены (MITM).

Подробнее: при handshake браузер проверяет сертификат сервера (подписан доверенным CA, домен совпадает, срок не истёк), стороны согласуют ключи (асимметрика на рукопожатии), дальше трафик шифруется быстрым симметричным шифром.

Подводные камни: HTTPS защищает канал, а не приложение: SQL-инъекции, XSS и кривую авторизацию он не отменяет. Заголовок HSTS говорит браузеру всегда ходить по HTTPS. В ASP.NET Core: UseHttpsRedirection + UseHsts в проде.

Исключения и надёжность

0/4

try / catch / finally — порядок выполнения

Коротко: try → если исключение → catch → в любом случае finally. finally выполняется всегда, кроме Environment.FailFast() и некоторых критических исключений ОС.

try
{
    var data = await LoadAsync();    // если исключение здесь
    Process(data);                   // → сюда не дойдём
}
catch (TimeoutException ex)          // ловим конкретное
{
    _log.LogWarning(ex, "Таймаут"); // обработка
    throw;                           // пробрасываем как есть (стектрейс сохранён)
}
catch (Exception ex) when (ex is not OperationCanceledException)  // фильтр
{
    _log.LogError(ex, "Неожиданная ошибка");
    throw new AppException("Ошибка обработки", ex);  // wrapping
}
finally
{
    _connection.Close();  // выполнится в ЛЮБОМ случае
}

Подводные камни: throw ex; затирает стектрейс — используй throw;. Несколько catch — порядок важен: от конкретного к общему. Exception filters (when) выполняются до входа в catch — полезно для логирования без поглощения исключения. Return внутри try — finally всё равно выполнится.

Практики работы с исключениями

Коротко: исключения — для исключительных ситуаций, не для управления потоком. Ловить — конкретные типы и только там, где можешь осмысленно обработать; остальное пусть летит в глобальный обработчик.

Подробнее: - catch (Exception) { } — «проглотить» ошибку: худшая практика, баги исчезают бесследно. - Перебрасывание: throw; сохраняет стектрейс, throw ex; — затирает (классический вопрос!). - Свои типы для домена: NotFoundException, DomainValidationException — глобальный обработчик замапит их в коды. - Фильтры catch (SqlException e) when (e.Number == 1205) — ловим только нужный случай, остальное летит дальше.

try { await ProcessAsync(); }
catch (ValidationException) { throw; }              // не наш уровень — пробрасываем как есть
catch (HttpRequestException ex)
{
    _log.LogWarning(ex, "Внешний сервис недоступен");
    throw new IntegrationException("Reviews API недоступен", ex);  // оборачиваем с контекстом
}

Как организовать глобальную обработку ошибок в ASP.NET Core?★

Коротко: один центральный обработчик вместо try/catch в каждом контроллере: в .NET 8+ — интерфейс IExceptionHandler (+UseExceptionHandler()), раньше — middleware. Он логирует исключение и возвращает клиенту единый формат ProblemDetails, без стектрейсов наружу.

public class GlobalExceptionHandler(ILogger<GlobalExceptionHandler> log) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext ctx, Exception ex, CancellationToken ct)
    {
        log.LogError(ex, "Unhandled exception, traceId={TraceId}", ctx.TraceIdentifier);

        var (status, title) = ex switch
        {
            NotFoundException      => (StatusCodes.Status404NotFound, "Ресурс не найден"),
            ValidationException    => (StatusCodes.Status400BadRequest, "Ошибка валидации"),
            _                      => (StatusCodes.Status500InternalServerError, "Внутренняя ошибка")
        };

        ctx.Response.StatusCode = status;
        await ctx.Response.WriteAsJsonAsync(
            new ProblemDetails { Status = status, Title = title, Extensions = { ["traceId"] = ctx.TraceIdentifier } }, ct);
        return true;
    }
}
// Program.cs:
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
builder.Services.AddProblemDetails();
app.UseExceptionHandler();

Подводные камни: в ответ клиенту — никакой внутрянки (стектрейс, SQL); детали — только в логи, наружу traceId для сопоставления. Ожидаемые бизнес-ситуации («email занят») — не исключения на 500, а осмысленные 4xx.

Retry, backoff и Polly — зачем?

Коротко: временные сбои (таймаут сети, 503, deadlock БД) лечатся повтором. Retry с экспоненциальным backoff — повторяем через растущие интервалы (1с, 2с, 4с) + jitter (случайный разброс), чтобы клиенты не били сервис синхронно. Polly — стандартная .NET-библиотека таких политик: Retry, Circuit Breaker, Timeout.

Подробнее: Circuit Breaker — «предохранитель»: после серии сбоев перестаёт долбить лежащий сервис и сразу возвращает ошибку, периодически пробуя восстановление. С HttpClientFactory политики вешаются на именованный клиент; в .NET 8+ есть AddStandardResilienceHandler() (Microsoft.Extensions.Http.Resilience поверх Polly) — retry + breaker + timeout из коробки.

builder.Services.AddHttpClient("reviews", c => c.BaseAddress = new Uri(apiUrl))
    .AddStandardResilienceHandler();   // .NET 8+: готовый набор политик

Подводные камни: ретраить можно только идемпотентные или дедуплицируемые операции — повтор POST «оплатить» без idempotency key = двойное списание. Всегда ограничивай число попыток и общий таймаут.

Архитектура приложения

0/5

Clean Architecture — слои и направление зависимостей★

Коротко: зависимости направлены внутрь, к домену: Domain (сущности, бизнес-правила — ни от чего не зависит) ← Application (use cases, объявляет интерфейсы инфраструктуры) ← Infrastructure (EF Core, внешние API — реализует эти интерфейсы) и API/Presentation (контроллеры, DI-составление).

Подробнее: ключевой трюк — инверсия зависимостей: Application говорит «мне нужен IReviewRepository», а Infrastructure отвечает «вот реализация на EF». Ядро (Domain + Application) не знает про EF, HTTP и очереди → его можно тестировать без базы и переносить между инфраструктурами.

Подводные камни: будь готов к «а не оверинжиниринг ли для маленького проекта?» — честный ответ: для CRUD-прототипа да, слоёв меньше; беру Clean Architecture, когда есть реальная бизнес-логика и нужна тестируемость ядра. Рассказывай на своём проекте: где лежат сущности, где интерфейсы, как подменяешь инфраструктуру в тестах — это ценят больше, чем пересказ схемы с кругами.

MVC, MVP, MVVM — архитектурные паттерны★

Коротко: Три паттерна для разделения UI и бизнес-логики. Все три разделяют Model (данные/логика), View (отображение) и промежуточный слой.

Подробнее:

MVC (Model-View-Controller): Controller обрабатывает запрос, берёт данные из Model, передаёт во View. Типично для веб: ASP.NET Core MVC — запрос → контроллер → возвращает View с данными.

Request → Controller → Model → Controller → View → Response

MVP (Model-View-Presenter): View пассивен (только отображение), Presenter реагирует на события View, обновляет View напрямую. Применяется в WinForms, Android.

View ←→ Presenter → Model

MVVM (Model-View-ViewModel): ViewModel — состояние и команды; View привязывается к ViewModel через data binding (двустороннюю). View не знает логики. Типично для WPF, Blazor, React/Angular.

View ←[binding]→ ViewModel → Model

Подводные камни: В веб-API архитектуре MVC-контроллер обычно тонкий — делегирует сервисам; жирный контроллер с бизнес-логикой — антипаттерн. MVVM строит на реактивных привязках: без нормального биндинга код MVVM превращается в MVP с лишним слоем.

CQRS и MediatR — зачем разделять команды и запросы?★

Коротко: CQRS — разделение операций изменения (Commands) и чтения (Queries): у них разные модели, оптимизации и пути кода. MediatR — реализация посредника: контроллер шлёт объект-запрос, медиатор находит его handler; контроллеры становятся тонкими, а сквозная логика (валидация, логирование, транзакции) вешается pipeline behaviors на все запросы сразу.

public record CreateReviewCommand(int ProductId, string Text, int Rating) : IRequest<Guid>;

public class CreateReviewHandler(AppDbContext db) : IRequestHandler<CreateReviewCommand, Guid>
{
    public async Task<Guid> Handle(CreateReviewCommand cmd, CancellationToken ct)
    {
        var review = Review.Create(cmd.ProductId, cmd.Text, cmd.Rating);
        db.Reviews.Add(review);
        await db.SaveChangesAsync(ct);
        return review.Id;
    }
}
// Контроллер: return Ok(await mediator.Send(command));

Подводные камни: CQRS ≠ обязательно две базы данных — в 90% проектов это разделение на уровне кода с одной БД (у чтения — Select в DTO без трекинга, у записи — доменная модель). Честно назови и минус: больше файлов/церемоний; на маленьком CRUD может быть overkill. Раз у тебя это в проекте (Sentio) — жди вопрос «зачем взял?» и отвечай про тонкие контроллеры + behaviors для валидации. Актуальное (с 2025): MediatR начиная с v13 — dual-license (Lucky Penny Software): бесплатно для OSS и компаний с выручкой < $5M в год, остальным нужна платная лицензия; v12.x остаётся свободной (Apache 2.0). Если спросят про альтернативы: свой mediator на паре интерфейсов + DI, source-generator Mediator, Wolverine.

Repository и Unit of Work — нужны ли поверх EF Core?

Коротко: честный ответ уровня middle: EF Core уже реализует оба паттерна — DbSet<T> ведёт себя как репозиторий, DbContext.SaveChanges — как Unit of Work. Свой слой репозиториев оправдан не «по канону», а по причинам.

Подробнее — когда свой репозиторий имеет смысл: - Clean Architecture: Application не должен ссылаться на EF → интерфейс IReviewRepository в Application, реализация в Infrastructure. - Инкапсуляция сложных запросов домена в одном месте (GetActiveWithPendingModeration() вместо копипасты Include-цепочек). - Подмена в unit-тестах без БД.

Подводные камни: анти-паттерн — generic repository IRepository<T> c GetAll(), возвращающим IQueryable: абстракция дырявая (EF торчит наружу), а тестировать проще не стало. Либо честные доменные методы, либо DbContext напрямую в handler'ах — обе позиции защищаемы, главное аргументировать.

Dependency Injection: что такое Container и Composition Root?

Коротко: DI-контейнер — реестр, который знает, как создавать зависимости и управляет их временем жизни (Transient/Scoped/Singleton). Composition Root — единственное место в приложении, где контейнер настраивается (в ASP.NET Core это Program.cs / builder.Services).

Подробнее: Без контейнера DI всё равно возможен (Pure DI: вручную создаёшь все зависимости в одном месте). Контейнер автоматизирует это и управляет скоупами. Принцип: объекты не создают свои зависимости сами (new), а получают их через конструктор. Это делает их тестируемыми и заменяемыми.

// Program.cs — Composition Root
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddScoped<IOrderRepository, EfOrderRepository>();
builder.Services.AddSingleton<IEmailSender, SmtpEmailSender>();

// OrderService — не знает откуда взялся репозиторий
public class OrderService(IOrderRepository repo, IEmailSender email)
{
    public async Task PlaceAsync(Order order)
    {
        await repo.SaveAsync(order);
        await email.SendAsync("admin@co", "Новый заказ");
    }
}

Подводные камни: «Service Locator» — антипаттерн: вместо получения через конструктор делаешь container.Resolve<IService>() внутри метода. Скрывает зависимости, усложняет тесты. Исключение — когда тип неизвестен до рантайма (IServiceProvider в фабриках). Всегда предпочитай Constructor Injection.

Паттерны проектирования

0/10

Что такое паттерны проектирования и зачем они нужны?

Коротко: Паттерны — проверенные решения типовых задач проектирования. Не готовый код, а шаблон мышления: «когда видишь такую ситуацию — структурируй код вот так». Дают общий язык в команде: «давай сделаем здесь Стратегию» понимают все.

Подробнее: Классификация GoF (Gang of Four) делит 23 паттерна на три группы: порождающие (создание объектов), структурные (организация классов и объектов), поведенческие (взаимодействие объектов).

Подводные камни: Паттерн — это инструмент, а не цель. «Я применил паттерн» ≠ «я написал хороший код». Overengineering через паттерны — реальная проблема: Simple Factory для одного типа объекта или Observer на три события раздувают код без пользы. Интервьюер оценит, если ты можешь обосновать, почему взял именно этот паттерн.

Порождающие паттерны — обзор

Коротко: Решают задачу создания объектов, скрывая детали инстанцирования от клиента. Основные: Singleton, Factory Method, Abstract Factory, Builder, Prototype.

Подробнее: - Singleton — гарантирует единственный экземпляр класса и глобальную точку доступа к нему. - Factory Method — определяет интерфейс для создания объекта, но конкретный тип решает подкласс. - Abstract Factory — создаёт семейства связанных объектов без привязки к конкретным классам. - Builder — пошаговое создание сложного объекта, разделяя конструкцию и представление. - Prototype — создаёт новый объект копированием (клонированием) существующего.

Singleton — что это и в чём проблема?★

Коротко: Singleton гарантирует один экземпляр класса в приложении и предоставляет глобальную точку доступа. Проблемы: скрытые зависимости, сложность тестирования, потокобезопасность, нарушение SRP.

Подробнее — типичная реализация с double-check locking:

public sealed class AppConfig
{
    private static AppConfig? _instance;
    private static readonly object _lock = new();

    private AppConfig() { }

    public static AppConfig Instance
    {
        get
        {
            if (_instance is null)
                lock (_lock)
                    _instance ??= new AppConfig();
            return _instance;
        }
    }
}
// Или проще: Lazy<T> потокобезопасен из коробки
public sealed class AppConfig2
{
    private static readonly Lazy<AppConfig2> _lazy = new(() => new AppConfig2());
    public static AppConfig2 Instance => _lazy.Value;
    private AppConfig2() { }
}

Подводные камни: Singleton — фактически глобальная переменная, которая скрывает зависимость. Тест, использующий Singleton, зависит от его состояния: тесты влияют друг на друга, порядок важен. Современная альтернатива: регистрировать тип в DI-контейнере как Singleton — контейнер гарантирует один экземпляр, но зависимость видна через конструктор и подменяема в тестах.

Фабричный метод vs Абстрактная фабрика

Коротко: Factory Method — один виртуальный метод создания одного типа объекта; подкласс решает какой именно. Abstract Factory — интерфейс для создания семейства взаимосвязанных объектов (кнопка + чекбокс + окно — все в одном стиле).

Подробнее:

// Factory Method: один метод, подкласс переопределяет
public abstract class Notifier
{
    public abstract IMessage CreateMessage(string text);   // factory method
    public void Send(string text) => CreateMessage(text).Deliver();
}
public class EmailNotifier : Notifier
{
    public override IMessage CreateMessage(string text) => new EmailMessage(text);
}

// Abstract Factory: семейство объектов
public interface IUIFactory
{
    IButton CreateButton();
    ICheckbox CreateCheckbox();
}
public class WindowsUIFactory : IUIFactory
{
    public IButton CreateButton()   => new WindowsButton();
    public ICheckbox CreateCheckbox() => new WindowsCheckbox();
}

Подводные камни: Частая ошибка путать с Simple Factory (статический метод с switch/if по типу) — это не GoF паттерн, но часто встречается в коде. Factory Method решает «КАК создать», Abstract Factory — «КАКОЕ СЕМЕЙСТВО создать».

Builder — когда и как?

Коротко: Builder нужен, когда объект создаётся пошагово с множеством опциональных параметров. Альтернатива телескопическим конструкторам.

var query = new QueryBuilder()
    .From("orders")
    .Where("status", "paid")
    .OrderBy("created_at", desc: true)
    .Limit(20)
    .Build();

Подводные камни: Для простых случаев Builder излишен — хватит object initializer или record with. Builder нужен, когда порядок шагов важен или когда нужно строить разные представления одного объекта (HTML-таблица vs PDF-таблица из одних данных).

Prototype — клонирование объектов

Коротко: Создаёт новый объект, копируя существующий. В C# реализуется через ICloneable (устаревший, возвращает object) или record with, или собственный метод Clone()/Copy().

Подробнее: Различие поверхностного (shallow) и глубокого (deep) копирования: shallow копирует ссылки (изменение во вложенном объекте затронет оба); deep копирует рекурсивно всё дерево объектов.

// record with — shallow copy из коробки
var original = new Config { Name = "prod", Tags = new List<string> { "a" } };
var copy = original with { Name = "dev" };  // Tags — та же ссылка! shallow

// Глубокое клонирование — вручную или через сериализацию/System.Text.Json
var deep = original with { Tags = new List<string>(original.Tags) };

Подводные камни: ICloneable не специфицирует shallow vs deep — это исторический косяк интерфейса, поэтому его избегают в пользу явных методов. В .NET 6+ для простых DTO deep copy удобно через JsonSerializer (serialize → deserialize).

Структурные паттерны — обзор и практика

Коротко: Определяют, как классы и объекты составляются в более крупные структуры. Основные: Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy.

Adapter — обёртка-переходник между несовместимыми интерфейсами. Классика: сторонняя библиотека с чужим интерфейсом оборачивается в адаптер, реализующий нужный тебе интерфейс.

// Старый логгер с чужим API → адаптируем под ILogger
public class LegacyLoggerAdapter(LegacyLogger legacy) : ILogger
{
    public void Log(string msg) => legacy.Write($"[APP] {msg}");
}

Facade — единая точка входа к сложной подсистеме. API-контроллер, вызывающий валидацию → сервис → репозиторий через одну публичную точку, — по сути фасад.

Proxy — заместитель объекта, добавляющий поведение (ленивая загрузка, кэш, проверка прав) прозрачно для клиента. EF Core использует прокси для lazy loading; Castle DynamicProxy — для перехвата вызовов в тестах.

Decorator — см. раздел 10 (у нас разобран подробно с кодом).

Паттерн Decorator — как добавить поведение, не меняя класс?

Коротко: обёртка с тем же интерфейсом, что у оборачиваемого объекта: добавляет поведение (кэш, логирование, метрики, retry) до/после делегирования внутрь. Клиент не отличает декоратор от оригинала.

public class CachedProductRepo(IProductRepo inner, IMemoryCache cache) : IProductRepo
{
    public async Task<Product?> GetAsync(int id) =>
        await cache.GetOrCreateAsync($"product:{id}", e =>
        {
            e.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
            return inner.GetAsync(id);
        });
}
// Регистрация: сначала SqlProductRepo, поверх — CachedProductRepo (вручную или Scrutor .Decorate)

Подводные камни: декораторы складываются в цепочки (кэш → логирование → метрики → реальный репозиторий). Отличие от наследования: композиция в рантайме, можно комбинировать; наследование фиксирует всё на компиляции.

Поведенческие паттерны — обзор и практика

Коротко: Определяют алгоритмы взаимодействия между объектами. Основные: Observer, Strategy, Command, Mediator, Iterator, Template Method, Chain of Responsibility, State.

Observer — объект (Subject) уведомляет подписчиков об изменениях. В C# реализован через event и делегаты. Примеры из жизни: подписка на события UI, реактивные стримы, INotifyPropertyChanged.

Command — запрос оборачивается в объект, что позволяет откладывать выполнение, ставить в очередь и откатывать. В ASP.NET + MediatR команды буквально так и называются — Commands.

Template Method — базовый класс определяет скелет алгоритма, конкретные шаги делегирует подклассам. Пример: DbMigration с абстрактными Up()/Down().

Chain of Responsibility — запрос передаётся по цепочке обработчиков, пока один не обработает. Конвейер middleware в ASP.NET Core — именно этот паттерн.

State — объект меняет поведение в зависимости от внутреннего состояния, как если бы он менял класс. Удобен для автоматов: заказ в состоянии Pending, Paid, Shipped, Cancelled ведёт себя по-разному.

Паттерн Strategy — что это и где применять?

Коротко: семейство взаимозаменяемых алгоритмов за общим интерфейсом; нужный выбирается в рантайме. Убивает разрастающиеся if/else/switch по типу поведения (расчёт скидки, способ доставки, формат экспорта).

public interface IDiscountStrategy { decimal Apply(decimal total); }
public class NoDiscount      : IDiscountStrategy { public decimal Apply(decimal t) => t; }
public class PromoDiscount   : IDiscountStrategy { public decimal Apply(decimal t) => t * 0.9m; }
public class VipDiscount     : IDiscountStrategy { public decimal Apply(decimal t) => t * 0.8m; }

// Выбор стратегии — по ключу через DI или фабрику
public class CheckoutService(IEnumerable<IDiscountStrategy> strategies) { /* ... */ }

Подводные камни: связка с Open/Closed из SOLID: новый вид скидки = новый класс, старый код не трогаем. Так и отвечай — «Strategy — это OCP в действии». Современный способ выбора реализации по ключу — keyed services (.NET 8+): AddKeyedScoped<IDiscountStrategy, VipDiscount>("vip") и получение через [FromKeyedServices("vip")].

Unit vs Integration тесты — в чём разница и что когда?★

Коротко: unit-тест проверяет единицу логики в изоляции (зависимости заменены моками): миллисекунды, точно указывает на сломанное место. Integration-тест проверяет связку компонентов с реальными зависимостями (API + БД): медленнее, но ловит то, что unit не видит — маппинги EF, SQL, конфигурацию DI, сериализацию.

Подробнее: пирамида: много unit (бизнес-логика, валидация, edge cases) → меньше integration (критичные сценарии API/БД) → минимум e2e. Инструменты integration в .NET: WebApplicationFactory<Program> поднимает приложение in-memory, Testcontainers — реальный PostgreSQL/SQL Server в Docker на время тестов.

Подводные камни: InMemory-провайдер EF — плохая замена интеграционным тестам: он не SQL (нет транзакций, констрейнтов, реального поведения запросов) — тесты зелёные, прод падает. Реальная БД в контейнере надёжнее.

Паттерн AAA и правила хорошего теста

Коротко: Arrange (подготовка данных и объекта) → Act (одно действие) → Assert (проверка результата). Имя теста описывает сценарий: Метод_Условие_ОжидаемыйРезультат.

[Fact]
public async Task CreateReview_WhenRatingOutOfRange_ThrowsValidationException()
{
    // Arrange
    var handler = new CreateReviewHandler(_dbMock.Object);
    var cmd = new CreateReviewCommand(ProductId: 1, Text: "ok", Rating: 11);

    // Act
    var act = () => handler.Handle(cmd, CancellationToken.None);

    // Assert
    await Assert.ThrowsAsync<ValidationException>(act);
}

Подводные камни: один тест — один логический сценарий; тесты независимы (не полагаются на порядок выполнения и общее состояние); проверяй и негативные пути, не только happy path. Хрупкий тест, который ломается от любого рефакторинга без изменения поведения, — тестирует реализацию, а не поведение.

Mock vs Stub, и что вообще мокать?

Коротко: stub — заглушка, которая просто возвращает заранее заданные данные («когда спросят GetUser(1) — верни вот этого»). Mock — объект, на котором проверяют взаимодействие («убедись, что SendEmail вызвали ровно один раз с этим адресом»). Библиотеки: Moq, NSubstitute.

var repo = new Mock<IProductRepo>();

Assert.Equal(90m, price);
repo.Verify(r => r.GetAsync(1), Times.Once);   // mock: проверка взаимодействия

Подводные камни: мокай свои интерфейсы на границах (репозиторий, почта, внешний API), а не всё подряд: тест, где замокано всё, проверяет моки, а не логику. DbContext напрямую мокается плохо — это ещё один аргумент за интерфейсы репозиториев или за интеграционные тесты с Testcontainers. Актуальное: после истории со SponsorLink (2023) многие команды перешли с Moq на NSubstitute; FluentAssertions с v8 (2025) стала платной для коммерческого использования — v7 бесплатна навсегда, есть свободный форк AwesomeAssertions.

Kafka и messaging

0/3

Что такое Kafka и из каких компонентов состоит?

Коротко: распределённая платформа потоковой передачи событий: по сути — реплицируемый журнал (log), из которого потребители читают сообщения в своём темпе. Ключевое отличие от классической очереди: сообщения не удаляются при чтении, а хранятся по retention-политике — их можно перечитать.

Подробнее — словарь: Broker — узел кластера; Topic — именованный поток сообщений; Partition — часть топика (единица параллелизма; порядок гарантируется только внутри партиции); Producer пишет, выбирая партицию по ключу сообщения; Consumer читает; Offset — позиция потребителя в партиции; Consumer group — потребители, делящие партиции между собой.

Подводные камни: «порядок сообщений гарантируется?» — только в рамках одной партиции; события одной сущности (заказ #42) шлют с одним ключом, чтобы они попали в одну партицию и сохранили порядок.

Что такое consumer group и как масштабируется чтение?

Коротко: consumer group — набор потребителей с общим group.id, совместно читающих топик: каждая партиция назначена ровно одному потребителю группы. Больше инстансов сервиса → партиции перераспределяются → горизонтальное масштабирование обработки.

Подробнее: разные группы независимы: топик «orders» одновременно читают группа биллинга и группа аналитики, каждая со своими offset'ами. Потребителей больше, чем партиций, — лишние простаивают: число партиций задаёт потолок параллелизма.

Подводные камни: при падении/добавлении потребителя происходит rebalance — партиции переназначаются, обработка группы на момент замирает. Мониторить нужно consumer lag (отставание offset'а от конца партиции) — главный сигнал, что потребители не справляются.

Гарантии доставки и идемпотентность потребителя

Коротко: типовой режим — at-least-once: сообщение доставится минимум один раз, но возможны дубликаты (например, consumer обработал, но упал до коммита offset'а). Поэтому обработчик обязан быть идемпотентным.

Подробнее — способы идемпотентности: естественный ключ + upsert; таблица processed message id (проверил-записал в одной транзакции с бизнес-изменением); идемпотентный producer (EnableIdempotence = true убирает дубли при ретраях продюсера) и транзакции Kafka для exactly-once внутри экосистемы.

var config = new ProducerConfig
{
    BootstrapServers = "localhost:9092",
    Acks = Acks.All,             // подтверждение от всех реплик
    EnableIdempotence = true      // без дублей при ретраях продюсера
};
using var producer = new ProducerBuilder<string, string>(config).Build();
await producer.ProduceAsync("orders",
    new Message<string, string> { Key = "order-42", Value = json });  // ключ → порядок в партиции

Подводные камни: сообщения, которые не удаётся обработать («ядовитые»), после N попыток отправляй в DLQ (dead letter topic), иначе они заблокируют партицию. Большие блобы в Kafka не льют — файл в объектное хранилище, в сообщении ссылка. Для «записать в БД и опубликовать событие атомарно» — паттерн Outbox.

Какие практики помогают писать чистый код в команде?

Коротко: маленькие функции с одной ответственностью, говорящие имена, ранний return вместо вложенности, явные зависимости через DI, тесты как страховка рефакторинга.

Подробнее: имя должно отвечать «что делает», без комментария (GetActiveSubscriptions, а не GetData2); магические числа — в именованные константы; команда фиксирует стиль автоматикой — .editorconfig, Roslyn-анализаторы, форматирование на CI — и не тратит ревью на пробелы. Code review смотрит на дизайн и читаемость, а не только «работает ли».

Подводные камни: «чистота» — не самоцель: рефакторинг без тестов — азартная игра; сначала тест, потом улучшение. Комментарии — про «почему», а не «что» (что — видно из кода).

Пример рефакторинга: разбить длинный метод

Коротко: метод, который валидирует, ходит в БД и собирает ответ, разбивается на шаги с именами — каждый можно понять и протестировать отдельно, а «оглавление» метода читается как сценарий.

// До: 80 строк — валидация, запросы, маппинг вперемешку
public async Task<IActionResult> CreateOrder(OrderRequest r) { /* всё сразу */ }

// После: метод читается как план
public async Task<IActionResult> CreateOrder(OrderRequest r, CancellationToken ct)
{
    var validation = Validate(r);
    if (!validation.IsValid) return BadRequest(validation.Errors);

    var order = await BuildOrderAsync(r, ct);
    await _repo.SaveAsync(order, ct);

    return CreatedAtAction(nameof(GetById), new { id = order.Id }, MapToDto(order));
}

Подводные камни: признаки, что пора делить: метод не влезает в экран, есть комментарии-заголовки секций («// теперь сохраняем»), больше 2–3 уровней вложенности. Guard clauses (ранние return) уменьшают вложенность лучше, чем else-лестницы.

Big O notation — нотация сложности алгоритмов★

Коротко: Big O описывает, как время выполнения или объём памяти алгоритма растёт с увеличением входных данных N. Константы и меньшие члены отбрасываются — важен порядок роста.

Подробнее — основные классы сложности:

Обозначение Название Пример
O(1) Константное Доступ к элементу массива по индексу
O(log N) Логарифмическое Бинарный поиск
O(N) Линейное Линейный поиск в несортированном списке
O(N log N) Линейно-логарифмическое QuickSort, MergeSort
O(N²) Квадратичное Пузырьковая сортировка
O(2ᴺ) Экспоненциальное Перебор всех подмножеств

Подводные камни: O(N) с малой константой быстрее O(log N) с огромной для маленьких N. Big O — асимптотика для больших N. На практике «кэш-дружественный» O(N) может быть быстрее O(log N) с разбросанными обращениями к памяти.

// O(1) — доступ по индексу
var x = arr[5];

// O(log N) — бинарный поиск
int i = Array.BinarySearch(sortedArr, target);

// O(N) — линейный поиск
var found = list.FirstOrDefault(x => x.Id == id);

// O(N²) — вложенный цикл (anti-pattern: Contains внутри foreach)
foreach (var a in listA)
    if (listB.Contains(a))  // Contains = O(N) → итого O(N²)
        ...
// Исправление: HashSet → O(N)

    if (setB.Contains(a)) ...  // O(1) per lookup

Алгоритм бинарного поиска★

Коротко: Находит элемент в отсортированном массиве за O(log N). Каждый шаг делит поисковое пространство пополам. 1000 элементов = максимум 10 шагов; 10^9 = 30 шагов. Именно поэтому за 32 итерации можно найти любой элемент в массиве до 4 миллиардов.

int BinarySearch(int[] arr, int target)
{
    int left = 0, right = arr.Length - 1;
    while (left <= right)
    {
        int mid = left + (right - left) / 2;   // избегаем overflow
        if      (arr[mid] == target) return mid;
        else if (arr[mid] < target)  left  = mid + 1;
        else                         right = mid - 1;
    }
    return -1;   // не найдено
}

Подводные камни: (left + right) / 2 может вызвать integer overflow при больших индексах — правильно left + (right - left) / 2. Обязательное условие — отсортированный массив. Для несортированных — хэш-таблица (O(1)) или сортировка + бинарный поиск (O(N log N + log N)).

Сортировки — основные алгоритмы

Коротко: QuickSort — O(N log N) средне, O(N²) worst case, in-place, не стабильный — стандарт в большинстве случаев. MergeSort — O(N log N) всегда, требует O(N) доп. памяти, стабильный. HeapSort — O(N log N) всегда, in-place. BubbleSort / InsertionSort — O(N²), используют для маленьких массивов или почти отсортированных данных.

Подробнее: Array.Sort в .NET использует IntroSort: QuickSort с fallback на HeapSort при глубокой рекурсии + InsertionSort для мелких подмассивов (< 16 элементов). LINQ OrderBy — стабильная сортировка (сравнение ключей с тай-брейком по исходному индексу; это не TimSort — TimSort используют Python и Java), поэтому цепочка OrderBy().ThenBy() корректно работает по нескольким полям.

Подводные камни: «Стабильность» сортировки — сохраняет ли она порядок одинаковых элементов. Важно при сортировке по нескольким полям: нестабильная сортировка по имени потом стабильной по возрасту — ОК; нестабильная оба раза — нет.

Что такое граф и обход в ширину (BFS)?

Коротко: Граф — набор вершин (nodes) и рёбер (edges) между ними. Может быть направленным/ненаправленным, взвешенным/невзвешенным. BFS (Breadth-First Search) обходит граф уровень за уровнем, используя очередь, — гарантирует кратчайший путь в невзвешенном графе.

void BFS(Dictionary<int, List<int>> graph, int start)
{
    var visited = new HashSet<int>();
    var queue   = new Queue<int>();

    queue.Enqueue(start);
    visited.Add(start);

    while (queue.Count > 0)
    {
        int node = queue.Dequeue();
        Console.WriteLine(node);

        foreach (var neighbor in graph[node])
        {
            if (!visited.Contains(neighbor))
            {
                visited.Add(neighbor);
                queue.Enqueue(neighbor);
            }
        }
    }
}

Подводные камни: DFS (глубина, через стек/рекурсию) vs BFS (ширина, очередь): DFS — меньше памяти для широких графов, BFS — гарантированно кратчайший путь в невзвешенном. Циклы в графе — обязательна проверка visited, иначе бесконечный цикл.

Алгоритм Дейкстры — поиск кратчайшего пути во взвешенном графе

Коротко: Жадный алгоритм: на каждом шаге выбирает непосещённую вершину с минимальным расстоянием от старта, обновляет расстояния до соседей. Подходит для неотрицательных весов. Сложность: O((V + E) log V) с priority queue.

Dictionary<int, int> Dijkstra(Dictionary<int, List<(int to, int w)>> graph, int src)
{
    var dist = graph.Keys.ToDictionary(k => k, _ => int.MaxValue);
    dist[src] = 0;

    // (distance, node)
    var pq = new PriorityQueue<int, int>();
    pq.Enqueue(src, 0);

    while (pq.TryDequeue(out var node, out var d))
    {
        if (d > dist[node]) continue;   // устаревшая запись в очереди — пропускаем
        foreach (var (to, weight) in graph[node])
        {
            int newDist = dist[node] + weight;
            if (newDist < dist[to])
            {
                dist[to] = newDist;
                pq.Enqueue(to, newDist);
            }
        }
    }
    return dist;
}

Подводные камни: Не работает с отрицательными весами (для этого — Bellman-Ford, O(VE)). A — эвристическое расширение Дейкстры: использует f(n) = g(n) + h(n), где h — приблизительное расстояние до цели (heuristic). A значительно быстрее для карт/сеток, если эвристика допустима (никогда не переоценивает).

Алгоритм A* — чем отличается от Дейкстры?new

Коротко: A* — это Дейкстра с подсказкой. Дейкстра расширяет вершины по фактической стоимости пути g(n), то есть растекается во все стороны равномерно. A* добавляет эвристику h(n) — оценку оставшегося расстояния до цели — и выбирает вершину с минимальным f(n) = g(n) + h(n), поэтому идёт преимущественно в сторону цели и просматривает меньше вершин.

Подробнее: ключевое условие корректности — эвристика должна быть допустимой (admissible): она никогда не переоценивает оставшееся расстояние. На сетке для перемещений по четырём направлениям берут манхэттенское расстояние, для восьми — диагональное, для свободного пространства — евклидово. Если h(n) = 0, A* вырождается ровно в Дейкстру. Если эвристика завышена — алгоритм станет быстрее, но найденный путь перестанет быть гарантированно кратчайшим.

Подводные камни: (1) A* нужен, когда есть одна конкретная цель и понятие «расстояния до неё»; если нужны кратчайшие пути до всех вершин — только Дейкстра. (2) Отрицательные веса не поддерживают ни Дейкстра, ни A* — там нужен Беллман-Форд. (3) Практический ответ на вопрос «где применял»: маршруты на карте, навигация по сетке, планирование в играх; в бэкенд-задачах чаще достаточно BFS или Дейкстры.

// A* на сетке: та же приоритетная очередь, но ключ = g + h
var open = new PriorityQueue<Point, int>();
open.Enqueue(start, Heuristic(start, goal));
var g = new Dictionary<Point, int> { [start] = 0 };

while (open.TryDequeue(out var cur, out _))
{
    if (cur == goal) break;
